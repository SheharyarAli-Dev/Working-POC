1. Executive Summary
The revised module should not be presented as “an AI vulnerability scanner that generates tests and fixes code.” That
formulation is too close to already-published 2026 detection-and-remediation pipelines. Instead, SATRA-RV retains the
strongest part of the original SATRA document — independent, change-targeted security assurance — and makes the
new components subordinate to a measurable acceptance problem: can an AI-generated application-code patch be
accepted only after deterministic security obligations, trusted security tests, validated dynamic tests, and isolated
before/after verification provide sufficient evidence that the targeted defect was removed without introducing a new
security regression?
The new core is therefore a five-part chain: (1) snapshot the trusted baseline and AI candidate, (2) build a Security
Change Contract from the diff and security semantics, (3) execute deterministic dictionary tests plus validated
Ollama-generated tests, (4) repair only from an evidence bundle and verify the candidate in a disposable sandbox, and
(5) accept/reject the patch with an auditable evidence record. The central research claim is deliberately bounded and

conditional: SATRA-RV is valuable only if this change-targeted, evidence-grounded gate detects security failures or
unsafe repairs that simpler baselines miss without creating unacceptable false blocks or local execution overhead.

 Core research question​
 Can a local, change-targeted security assurance gate improve the safety of AI-generated application-code changes by
 combining trusted security tests with validated adaptive tests and differential repair verification, while remaining independent
 of external APIs and avoiding circular trust in the same AI system that generated the patch?

The design therefore does not abandon SATRA. It extends its strongest research idea — independent security assurance
after AI-generated change — into a complete detection-to-repair-to-verification loop. The repair loop is a downstream
consumer of the assurance model, not the source of the research novelty.



4. Exact Pain Point and Real Use Case
The direct pain point is not “AI writes insecure code” in isolation. Static vulnerability scanners already identify many
known patterns, and LLMs can already propose fixes. The more difficult engineering problem is deciding whether an
AI-generated change is safe to accept when the same change can alter code, tests, assumptions and behavior at once.
Representative safe use case: a coding agent modifies a Flask endpoint that previously required authentication and
ownership checks. The patch makes the normal functional test pass, but the changed code path now permits an
unauthorized access path. A static scanner may miss a semantic authorization regression; the old suite may also pass.
SATRA-RV uses the diff to localize the security-sensitive region, runs deterministic authorization tests, asks Ollama for
additional repository-specific tests, validates useful dynamic tests against bounded counterfactuals, and only accepts a
repair after isolated before/after security and functional checks succeed.

 One-line problem statement​
 AI-generated application changes can introduce or preserve security defects, and a green ordinary test suite is insufficient
 evidence of safe repair. SATRA-RV provides a local, change-targeted security evidence gate that tests, repairs, re-tests,
 isolates and differentially verifies the candidate before acceptance.

9. Security Dictionary Design
The dictionary is not a static list of payloads. It is a versioned security knowledge/test specification that connects a
vulnerability family to preconditions, code patterns, expected safe behavior and executable pytest logic. It becomes the
trusted deterministic layer against which Ollama-generated tests are judged.
SecurityRule {
  id: AUTHZ.IDOR.001
  cwe: CWE-639
  family: "authorization / object ownership"
  applicability: [Flask, pytest]
  preconditions: [object_id_from_request, user_context, ownership_check]
  security_obligation: "non-owner must be denied"
  safe_outcome: [HTTP_403, no_state_change]
  test_template: pytest_function
  input_classes: [owner, non_owner, unauthenticated]
  counterfactual_template: "remove_or_bypass_owner_check"
  validation_rules: [runs, discriminates, stable, local]
  version: 1
}

10. Ollama Dynamic Test Generation and Validation



                   Figure 3. Ollama-generated tests are hypotheses; only validated candidates enter the trusted execution set.


10.1 Why dynamic tests are included
A deterministic dictionary cannot anticipate every repository-specific security invariant. Different applications encode
authorization, object ownership, URL constraints and validation logic differently. A local model can use the exact changed
code context to propose additional cases. Current 2026 evidence supports this direction but also shows that
LLM-generated tests can be weak or brittle, so the generator must remain subordinate to an independent validator.
SWE-Mutation found substantial weaknesses in the discriminative power of current LLM-generated suites, while a 2026
security-test-generation study demonstrated that adversarial test synthesis can improve fault discovery when paired with
mutation/oracles.

10.2 Dynamic-test context policy
●​   Only changed security slices are sent to the model by default. The context builder can include the changed function,
     relevant call/data flow, applicable dictionary entries, route/schema signatures and small neighboring utilities.
●​   No production secrets or user data are allowed. Redaction and repository policy checks happen before the model
     call.
●​   No model call occurs when deterministic tests and security analysis already provide sufficient evidence. This makes
     Ollama conditional rather than mandatory.
●​   The model returns structured test candidates. The system rejects prose-only outputs and refuses unsafe side effects.
●​   The model is never the final judge. Acceptance is determined by deterministic execution and counterfactual evidence.

11. Automated Repair and Sandboxed Verification




                      Figure 4. Repair loop: candidate patch → isolated execution → differential evidence → accept/retry/reject.


11.1 Repair contract
Ollama receives a structured evidence bundle rather than a generic “fix security” prompt. The bundle identifies the
affected region, finding family, expected secure behavior, failing tests, accepted dynamic tests, relevant static signals and
                              ASENT | SATRA-RV | Revised Module Design | 25 September 2026 | Page 8
constraints on the patch. The repairer proposes a patch; it cannot mark the patch safe and it cannot directly write the final
commit.

11.2 Sandbox controls
●​   Disposable execution. Every candidate patch runs in a fresh container or isolated workspace and is destroyed after
     evaluation.
●​   No production credentials. Benchmark and local evaluation use synthetic data; secrets are excluded from the
     container.
●​   Restricted network. Default repair verification runs without outbound network access unless a benchmark explicitly
     needs a controlled local service.
●​   Bounded resources. CPU, memory, filesystem and wall-clock limits stop pathological patches/tests.
●​   Clean dependency state. Dependencies are prepared from a controlled local build environment; the sandbox does
     not rely on mutable developer state.
●​   Before/after differential. The same security obligations and functional invariants are executed against baseline and
     candidate where possible.

12. Decision Engine and Evidence Model
The system should expose four final states: ACCEPTED, REJECTED, RETRY_AVAILABLE and INCONCLUSIVE. The
original SATRA labels PRESERVED_WITHIN_MODEL, ORACLE_WEAKENED, APPLICATION_REGRESSION,
PRE_EXISTING_TEST_GAP and INCONCLUSIVE remain useful internally for diagnosis; the external gate can
summarize them into a merge decision.
if insufficient_evidence:
    decision = INCONCLUSIVE
elif patch_violates_security_contract:
    decision = REJECTED
elif trusted_tests_fail or accepted_dynamic_tests_fail:
    decision = REJECTED
elif new_security_regression:
    decision = REJECTED
elif functional_regression or build_failure:
    decision = REJECTED
elif repair_attempts_remaining and failing_evidence_is_actionable:
    decision = RETRY_AVAILABLE
else:

22. Panel-Critic Questions and Direct Answers
“Isn’t this just Semgrep/Bandit + Ollama?”
Not in the proposed research definition. Those tools are explicit baselines. SATRA-RV adds a change-targeted security
contract, trusted security-test dictionary, validation of LLM-generated tests, controlled repair, and differential before/after
patch acceptance. Whether that added chain is actually useful must be demonstrated experimentally.

“Isn’t Ollama just an existing technology?”
Yes. Ollama is infrastructure, not the contribution. The student contribution is the protocol that controls when Ollama is
called, what context it sees, how its tests are validated, how patches are constrained, and how the final verdict is
generated independently.

“Why not just run all tests?”
Because passing tests does not prove that the tests remain discriminative and does not guarantee that a repair
introduced a new security failure. Current 2026 research documents both test-suite weaknesses and repair-induced
security regressions.

“Why do you need the dictionary if Ollama can generate tests?”
The dictionary is the trusted deterministic floor. It prevents the research from depending entirely on model behavior and
provides reproducible ground truth for benchmarking the dynamic layer.




                                 ASENT | SATRA-RV | Revised Module Design | 25 September 2026 | Page 14
“Why do you need dynamic tests?”
Repository-specific security semantics may not be captured by fixed rules. The dynamic layer explores local behavior, but
only accepted candidates are promoted to the execution set.

“Why do you need sandboxing?”
A patch can remove the target finding while changing functionality or introducing a second vulnerability. A disposable
environment allows differential verification without touching production or the developer’s main workspace.

“How do you know your dynamic test is good?”
It must run on the secure baseline, detect a valid security counterfactual, remain stable, stay local to the target behavior
and produce reproducible evidence.

“Can you guarantee the application is secure?”
No. The module makes a bounded claim about the supported Python/web security model and tested obligations.
Universal security is explicitly out of scope.

“Where is the students’ work?”
In the security-change localizer, contract model, dictionary design, pytest harness, test validator, evidence correlator,
differential sandbox verifier, decision engine, benchmark, baselines, ablations and empirical evaluation. Existing tools are
components under test, not the project itself.



23. Final Research Claim and Green-Light Criteria
Recommended claim language: “SATRA-RV investigates whether a local, change-targeted security assurance gate that
combines trusted security obligations, deterministic security tests, validated adaptive tests and differential post-repair
verification can reduce silent security regressions in AI-generated Python web-application changes compared with
simpler scanning, test-replay and repair pipelines.”
Do not claim “first,” “state of the art,” “fully secure,” or “solves AI security” until the empirical results support those
statements. The original SATRA document correctly treated novelty as conditional; the revised design should preserve
that discipline.

25. Absolute Limitations / What This Document Does NOT Claim
●​     No universal vulnerability coverage. The security dictionary and contract model are bounded.
●​     No guarantee of zero false negatives. The system can miss issues outside its rule/model space.
●​     No guarantee that Ollama is always correct. The architecture explicitly assumes the opposite and validates model
       output.
●​     No guarantee that every repair can be automated. INCONCLUSIVE/REJECTED/human-review outcomes are
       legitimate outputs.


                              ASENT | SATRA-RV | Revised Module Design | 25 September 2026 | Page 16
●​   No proof that the research is novel before experiments. The current 2026 literature makes overlap substantial; the
     claimed contribution must survive baselines and kill tests.
●​   No paid API requirement. Optional external tooling may be useful for comparison only and is not part of the required
     core.
●​   No claim that sandboxing itself is novel. It is a required safety mechanism in this architecture, not the research
     contribution by itself.



26. Final Verdict
 GREEN LIGHT TO PROCEED TO IMPLEMENTATION — WITH A CONDITIONAL NOVELTY GATE​
 The merged design is strong enough to build and defend as a serious FYP module. The correct research posture is not “we
 invented automated security fixing”; that area is already crowded. The defensible contribution is the independent, local,
 change-targeted assurance protocol that makes deterministic tests, adaptive tests, repair proposals and sandbox results
 converge into a commit decision, with explicit measurements against strong simpler baselines.



For the committee, the simplest direct explanation is: “Our module does not trust the AI patch, does not trust AI-generated
tests, and does not trust a green ordinary test suite. We build a security contract from what changed, run trusted security
tests, use a local model only to discover additional tests or propose a repair, validate those tests independently, run the
repair in a disposable environment, compare security and functional behavior before and after, and commit only when the
evidence gate passes.”
That formulation keeps the original SATRA research backbone, makes your new dictionary/Ollama/sandbox choices
first-class implementation components, directly answers the previous committee criticisms, and gives the module enough
genuine technical and experimental work for a 12-month contribution. The final green light on novelty depends on the
empirical results defined above.
