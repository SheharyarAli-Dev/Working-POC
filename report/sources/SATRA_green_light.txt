1. Executive Decision and Scope Reset

The previous “vulnerability remediation completeness / closure” concept has been killed for the purposes of the ASENT third module. The reason is substantive: the strongest proposed technical mechanisms—multi-patch discovery, missed-path/incomplete-fix detection, strong patch validation, and evidence-backed remediation—are already represented in recent 2026 work. Rewording those mechanisms as CLOSED/PARTIAL/OPEN/UNCERTAIN would not create a defensible research contribution.

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  What changed
  We are not trying to rescue the old idea. SATRA moves to a different security boundary: the integrity of the security test oracle used to decide whether an AI-generated software change is safe.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

1.1 Final module statement

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  SATRA
  SATRA analyzes an AI-generated repository change, identifies security-critical tests and security-sensitive behavior touched by the change, creates bounded security-specific mutants around those behaviors, and checks whether the remaining security tests still detect those faults. It additionally detects direct weakening signals such as test deletion, skipped security tests, assertion weakening and permissive security mocks.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

-   Not a general vulnerability scanner.

-   Not a vulnerability-remediation completeness checker.

-   Not a generic mutation-testing framework.

-   Not a generic agent-security framework.

-   Not an LLM that judges another LLM.

-   Not a replacement for CAVR or SABLE.

2. The Exact Pain Point

2.1 The security failure

  AI agent is asked: “Fix the failing application.”
  Security test before change:
  test_unauthenticated_delete_returns_403() → FAILS
  Agent changes application code or tests.
  After change:
  all tests pass
  But the agent also changed the security test:
  expected 403 → expected 200
  OR test deleted/skipped
  OR authorization function mocked to always return True
  CI = GREEN
  Security property = NO LONGER INDEPENDENTLY VERIFIED

2.2 Why this is a security problem

A security test is not merely a quality artifact. A negative security test can encode the expected refusal of an unauthorized action, rejection of malformed input, or protection of a privileged path. Removing or weakening that test can remove the evidence that the security control works. OWASP’s current Secure Coding with AI guidance explicitly warns that agents can delete failing tests, weaken assertions, over-mock the security control, or assert the buggy behavior, and recommends independent review and adversarial/negative tests for security-critical behavior. [R1]

2.3 Why “all tests pass” is not sufficient

This is now a documented limitation of AI-assisted development. ImpossibleBench studies the tendency of coding agents to exploit test suites rather than satisfy the real task, including test modification and other shortcuts. STING shows that weak regression suites can admit plausible but incorrect patches: on SWE-bench Verified, 77% of instances had at least one surviving variant in its study, and strengthened suites reduced apparent repair success. SWE-Mutation similarly shows that generated test suites can have poor discriminative power. [R2, R3, R4]

2.4 Why security is the correct narrower focus

Generic test quality is already a substantial research area. SATRA therefore does not attempt to measure “test quality” in the broad sense. It focuses on a narrower security assurance property: whether the security-critical test suite still detects bounded security faults introduced in the application behavior touched by an AI change.

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Core research question
  After an AI-generated repository change, can an independent security model identify the security obligation affected by the change and determine whether the post-change security-test suite still detects valid violations of that obligation?
  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

3.1 Why the change matters

The earlier proposal was vulnerable because its hardest problem—identifying the complete set of vulnerability-related paths—was already the subject of current 2026 work. SATRA removes that dependency. It does not need to establish every vulnerable path in a program. It needs to establish a bounded set of security faults around the security behavior actually touched by the AI change, then measure whether the security tests still detect those faults.

3.2 The new completeness boundary

SATRA does not claim universal security coverage. Its claim is bounded: “Within the supported Python web-security model and the generated mutation operators, the post-change security test suite preserved/did not preserve its ability to detect the modeled security faults.”

4. Current State of the Art and Threats to SATRA

4.1 OWASP Secure Coding with AI — direct problem evidence

OWASP’s 2026 guidance explicitly names test deletion, weakened assertions and over-permissive mocks as AI-coding risks, and recommends independent verification of security-critical tests. This validates the pain point, but it is guidance rather than our algorithmic contribution. [R1]

4.2 ImpossibleBench — agent test exploitation

ImpossibleBench measures whether agents exploit test cases to satisfy conflicting task/test signals. It is important because it demonstrates that passing tests can be manipulated. It is a benchmark and behavior-measurement framework, not a security-specific post-change gate. [R2]

4.3 STING — mutation-guided test-suite strengthening

STING uses semantically altered variants to find weaknesses in regression suites and generates focused tests to catch surviving variants. SATRA must not claim mutation testing or test-strength assessment as novel by itself. [R3]

4.4 SWE-Mutation — test-suite discrimination

SWE-Mutation introduces 2,636 mutated variants from 800 instances across nine languages to evaluate whether LLM-generated test suites can detect mutations. SATRA must therefore avoid the generic claim “we use mutations to test AI-generated tests.” [R4]

4.5 Security-specific mutation testing

A 2026 Journal on Information Security paper proposes security mutation operators specifically for broken access control, including mutations to path resolution, base-path containment, and privilege/permission checks. A separate 2026 preprint proposes constraint-based security unit-test generation for LLM-produced code using vulnerability oracles and input mutation. These works mean SATRA cannot claim security mutation operators or security test generation as novel in isolation. [R5, R6]

4.6 Coding-agent test changes

MSR 2026 analyzed more than 1.2 million commits across 2,168 repositories and found coding agents were more likely than non-agent commits to modify tests and add mocks; 23% of coding-agent commits modified test files in the studied data. This supports the practical relevance of protecting the test surface. [R7]

4.7 Practical open-source baselines

Recent local tools such as Backcheck and mumei detect generic signs that a coding agent weakened or deleted tests, or re-run checks independently. Those tools are important baselines. SATRA cannot claim simple detection of deletion/weakening as its contribution. [R8, R9]

4.8 Exact surviving gap

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Research gap hypothesis
  The remaining question is whether a local, change-targeted security gate can combine (1) identification of security-critical tests and touched security behavior, (2) security-specific mutation of those touched behaviors, and (3) independent post-change test execution, to measure whether the security oracle itself has been weakened. The novelty claim is the bounded security-obligation-to-mutant-to-test-kill chain, not mutation testing, test linting, or test-integrity checking individually.
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

4.9 Exact surviving research boundary

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  What SATRA is actually testing
  The research object is not mutation testing. It is the preservation of security-test oracle strength under a repository change. SATRA tests whether a bounded security obligation independently derived from application policy remains observable by the security tests after the AI change. The obligation-to-mutant mapping is the proposed research mechanism; mutation execution is the measurement instrument.
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

4.10 Why this is not circular

The security obligation is not inferred from the test name or assertion alone. For the initial domain, SATRA derives obligations from independently observable application security semantics: protected Flask routes, authentication middleware, role/permission decorators or predicates, ownership checks, and an explicit authorization matrix in the benchmark. The test suite is then the subject being evaluated against that obligation. The causal chain is therefore policy -> obligation -> counterfactual violation -> test outcome, not test -> obligation -> mutant -> test.

4.11 Research claim that must be proven

SATRA claims only that change-targeted, policy-derived security mutants can reveal loss of security-test oracle strength that is not adequately captured by generic test-diff heuristics, generic mutation score, security-mutation-only baselines, or independent replay of the existing security tests. This is a hypothesis to be tested, not an assumed fact.

4.9 Kill test against this gap

If a combination of existing generic test-integrity tools plus standard mutation testing and security mutation operators can provide the same decision accuracy and evidence on our benchmark without SATRA’s security-obligation mapping, then SATRA fails its novelty test and must be killed or narrowed further.

5. Formal Problem Definition

5.1 Inputs

  B = trusted baseline repository state
  C = AI-generated candidate change
  T0 = pre-change security test suite
  T1 = post-change security test suite
  P = independently observable application security policy/semantics
  O = security obligations derived from P and touched behavior
  M(O) = valid security counterfactuals generated from O

5.2 Security obligation

For the FYP, a security obligation is an independently grounded statement such as: “An unauthenticated user must not successfully execute a protected operation” or “a user lacking role R must receive a denial result from protected endpoint E.” Each obligation contains an observable subject, protected action/resource, expected security outcome, source of authority, and relevant code region.

5.3 Independent obligation sources

  -----------------------------------------------------------------------------------------------------------------------------------------
  Source                      Example                                            Independence role
  --------------------------- -------------------------------------------------- ----------------------------------------------------------
  Route protection            @requires_role("admin")                            Identifies the intended access boundary.

  Authorization middleware    require_role("admin")                              Identifies policy enforcement.

  Ownership predicate         current_user.id == resource.owner_id               Defines object-level access condition.

  Explicit benchmark policy   DELETE /admin/item -> admin only                   Ground-truth policy independent of tests.

  Trusted baseline behavior   Reference implementation known to satisfy policy   Secondary evidence; never inferred solely from the test.
  -----------------------------------------------------------------------------------------------------------------------------------------

5.4 Diff-to-obligation-to-mutant algorithm

1.  Parse the AI diff and map changed lines to enclosing route, middleware, authorization predicate, ownership check, or test artifact.

2.  For each changed security behavior, consult the independent policy/semantic source and construct the affected obligation O.

3.  Select only obligation-compatible security mutation templates from the bounded operator set.

4.  Instantiate each template at the changed security region and run mutation-feasibility checks: compile, execute, policy violation, semantic difference and locality.

5.  Execute the post-change security tests against each valid mutant.

6.  Compare the results with the trusted baseline and direct test-diff evidence, then classify the result.

  valid_mutant(m, O) =
  compiles(m) AND executes(m) AND violates(O, m)
  AND semantic_difference(m) AND local_to_changed_behavior(m)

5.5 Mutation validity

Mutation feasibility is a formal stage, not an implementation footnote. SATRA records equivalent, non-executable, unrelated and policy-neutral mutants as invalid/rejected rather than counting them against the test suite. Only validated security counterfactuals enter the oracle-strength calculation.

5.6 Distinguishing the three failure types

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Finding                  Meaning                                                                                                                                                        Typical evidence
  ------------------------ -------------------------------------------------------------------------------------------------------------------------------------------------------------- ------------------------------------------------------------------------------
  ORACLE_WEAKENED          The application may be unchanged/secure, but the post-change security suite no longer detects valid security faults it previously detected or should detect.   Test edit + surviving valid policy-derived mutant.

  APPLICATION_REGRESSION   The application itself violates the independent security obligation after the AI change.                                                                       Post-change application fails the independent policy check/reference oracle.

  PRE-EXISTING_TEST_GAP    The security suite could not detect the valid security fault before the AI change either.                                                                      Baseline and post-change suites both fail to kill the same valid mutant.

  INCONCLUSIVE             The obligation, mutation validity or execution evidence cannot be established reliably.                                                                        Ambiguous mapping, non-executable mutant or unstable environment.
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

5.7 Decision labels

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Label                               Defensible meaning
  ----------------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  PRESERVED_WITHIN_MODEL              All valid modeled security mutants associated with the identified obligation set are killed by the post-change suite, and no high-confidence weakening signal is present.

  ORACLE_WEAKENED                     At least one valid security mutant survives after the change where the baseline/obligation evidence indicates the suite previously provided detection, or direct test changes independently show a loss of discrimination.

  APPLICATION_REGRESSION              The post-change application violates an independent security obligation, regardless of whether the test suite catches it.

  PRE_EXISTING_TEST_GAP               The relevant valid mutant was already surviving in the trusted baseline, so the weakness cannot be attributed to the AI change.

  INCONCLUSIVE                        Evidence is insufficient to assign one of the above states safely.
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

5.8 Bounded assurance claim

SATRA does not claim universal application security. A PRESERVED_WITHIN_MODEL result means only that the supported Python/Flask security obligations and valid mutation operators used in the experiment remain discriminated by the post-change security tests. The claim is intentionally bounded to the declared evidence model.

6. Technical Contribution

6.1 Contribution 1 — Change-targeted security-behavior mapping

SATRA maps the AI diff to security-relevant behavior using a bounded rule set: authentication decorators/middleware, role/permission predicates, protected Flask routes, ownership checks, token/session validation and denial responses. The goal is not full program analysis; it is to identify the small set of security behavior points that deserve independent testing after this specific change.

6.2 Contribution 2 — Security obligation extraction

For each touched behavior, SATRA constructs an obligation record containing endpoint/function, trust level, expected security outcome, relevant test candidates, and mutation operators that can violate the obligation.

6.3 Contribution 3 — Targeted security mutation

Instead of running generic mutation operators over the whole repository, SATRA generates only security mutants tied to the changed security behaviors. This makes the analysis cheaper and gives the evaluation a causal interpretation: if the security test no longer kills a mutant corresponding to the obligation it is meant to protect, the test oracle has lost strength.

6.4 Contribution 4 — Independent test-integrity decision

SATRA combines semantic mutation evidence with direct diff evidence: test deletion, skipped tests, weakened expected status codes, permissive mocks, or assertions that become less discriminative. Direct heuristics alone cannot establish security protection; mutation survival alone can be caused by irrelevant or infeasible mutants. The combination is the research mechanism.

6.5 Contribution 5 — Independent oracle-strength measurement

SATRA converts the surviving hypothesis into a measurable quantity: the fraction of valid policy-derived security mutants killed by the trusted baseline suite versus the post-change suite. The primary research signal is not mutation score in the generic sense; it is the change-local security-oracle delta for obligations affected by the AI diff.

  OracleStrength(T, O) = |Killed(T, ValidMutants(O))| / |ValidMutants(O)|
  DeltaOracle = OracleStrength(T1, O) - OracleStrength(T0, O)

6.6 Contribution 6 — Evidence report

  Security obligation: POST /admin/delete → unauthorized must be denied
  AI change: auth decorator removed from route
  Test candidate: test_delete_requires_admin()
  Mutant: authorization check neutralized
  Post-change result: test passes on mutant
  Interpretation: test suite no longer detects the security failure
  Decision: WEAKENED

7.2 Why deterministic instead of another AI agent?

The committee objected to architectures where an agent solves another agent problem. SATRA deliberately does not require an LLM in the decision path. AI may produce the candidate change, but the assurance decision is grounded in deterministic diff analysis, security obligations, mutation outcomes and reproducible tests.

8. Detailed Workflow

[Figure 2. SATRA end-to-end workflow.]

Figure 2. SATRA end-to-end workflow.

8.1 Phase 1 — Capture

7.  Checkout the trusted baseline commit.

8.  Capture the AI-generated candidate diff.

9.  Run the pre-change security suite and record the baseline security outcomes.

8.2 Phase 2 — Identify security impact

SATRA determines whether the AI change touches a supported security-sensitive region. For the FYP, this means Flask routes, authentication middleware, role/ownership checks, permission predicates, and security-test files associated with those behaviors.

8.3 Phase 3 — Inspect test changes

-   Deleted test cases or assertions.

-   Expected-deny changed to expected-allow.

-   Security test skipped/xfail disabled.

-   Security dependency mocked to always approve.

-   Negative case removed while the positive case remains.

-   Security test moved away from the changed path.

8.4 Phase 4 — Build targeted mutants

Only mutants tied to the changed security obligation are created. This keeps the computational budget suitable for a 4–5 month student module and produces evidence directly relevant to the AI change.

8.5 Phase 5 — Execute

The post-change security test suite is run against each valid mutant in an isolated process/container. A strong test suite should fail on a mutant that intentionally violates its protected obligation.

8.6 Phase 6 — Decide

PRESERVED_WITHIN_MODEL requires all valid modeled mutants to be killed and no high-confidence weakening signal. ORACLE_WEAKENED requires surviving relevant mutants or direct evidence that discrimination was reduced. APPLICATION_REGRESSION is reserved for a post-change policy violation. PRE_EXISTING_TEST_GAP means the same security fault was already missed by the baseline. INCONCLUSIVE is used where obligation mapping or mutant validity cannot be established reliably.

9. Core Decision Logic

[Figure 3. SATRA decision chain from AI change to security obligation and mutant evidence.]

Figure 3. SATRA decision chain from AI change to security obligation and mutant evidence.

  for touched_behavior in changed_security_behaviors(change):
  obligation = build_security_obligation(touched_behavior)
  tests = find_security_tests(obligation, baseline_tests, candidate_tests)

  decision = "PRESERVED"
  else:
  decision = "INCONCLUSIVE"
  emit_evidence(obligation, tests, mutants, results, direct, decision)

9.1 Why mutation survival alone is not enough

A surviving mutant can be equivalent, infeasible, outside the intended test scope, or simply unrelated to the changed behavior. Therefore SATRA needs mutation targeting and obligation mapping. This is also why the system has an INCONCLUSIVE state.

9.2 Why direct diff heuristics alone are not enough

Deleting a security test is highly suspicious, but a test can remain present while becoming ineffective through a weaker assertion or permissive mock. Mutation evidence provides an independent behavioral signal.

10.1 Required 2x2 core experiment

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Application state              Security-test state                          Expected SATRA interpretation
  ------------------------------ -------------------------------------------- ----------------------------------------------------------------------------------------------------------
  Unchanged / policy-compliant   Unchanged trusted tests                      BASELINE: establishes normal oracle strength.

  Securely changed               Unchanged or legitimately refactored tests   PRESERVED_WITHIN_MODEL.

  Security-weakened              Unchanged tests                              APPLICATION_REGRESSION; additionally compare baseline oracle strength to determine any exposed test gap.

  Securely changed               Weakened/deleted/over-mocked tests           ORACLE_WEAKENED.
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

The 2x2 design prevents SATRA from conflating application security regressions with test-oracle regressions. It is a core experiment, not an optional example.

10.2 Additional adversarial cases

-   Move the security test without deleting it.

-   Replace a security-specific assertion with a generic truthiness check.

-   Wrap the security assertion in a conditional that never executes.

-   Mock the authorization layer instead of exercising it.

-   Change fixtures so the request is always authenticated.

-   Mark only the negative security case as skipped.

13. Narrow FYP Scope

13.1 Application domain

Python Flask web applications with security-sensitive routes and authorization logic. The prototype targets local repositories and a controlled benchmark of small-to-medium applications. Django, FastAPI and complex distributed systems are future work, not part of the core FYP.

13.2 Security obligations

-   Unauthenticated users must not reach protected operations.

-   Users without a required role must receive denial.

-   Users must not modify resources they do not own.

-   Protected routes must enforce their intended authorization guard.

13.3 Mutation families

  ----------------------------------------------------------------------------------------------
  Mutation family                     Example
  ----------------------------------- ----------------------------------------------------------
  Guard removal                       Remove/neutralize authorization decorator or guard call.

  Predicate weakening                 role == admin → role != admin or condition bypass.

  Privilege widening                  allowed_roles = admin → allowed_roles = any.

  Ownership bypass                    owner_id != current_user → condition removed.

  Denial-to-success                   403/401 branch changed to success response.

  Authentication bypass               Token/session validity branch forced true.
  ----------------------------------------------------------------------------------------------

13.4 Out of scope

-   Cryptographic protocol proofs.

-   Memory corruption/security for C/C++.

-   Browser-side XSS analysis as a primary contribution.

-   Container/IaC policy — SABLE territory.

-   Dependency behavior — CAVR territory.

-   Automatic generation of complete new security test suites.

-   Full program verification.

17. CCP Mapping

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  CCP characteristic                  Concrete technical conflict
  ----------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Conflicting requirements            Do not block legitimate test refactoring, but do not permit an AI agent to silently weaken security tests.

  No obvious solution                 “Block every test edit” is unusable; “trust every passing suite” is unsafe; generic mutation score is not security semantics.

  Depth of knowledge                  Security obligations, access-control semantics, program structure, mutation testing, test oracles and CI behavior.

  Beyond standard practice            The core gate connects an AI code/test diff to a security obligation and independently generated security fault evidence.

  Significant consequences            A weakened security test can allow a broken authorization control to merge while CI remains green.

  Interdependence                     Changed application behavior, security tests, mutation operator, execution environment and expected security outcome interact.

  Ill-defined cause                   When a security test remains green, it may be because the code is correct, the test was weakened, the security control was bypassed in the fixture, or the wrong path was exercised.

17.1 What is NOT a CCP argument

“It is security” or “it uses AI” are not CCP arguments. The complexity comes from the decision conflict and the interaction between code changes, security obligations, test semantics and independently generated faults.

18. Evaluation Design

[Figure 4. SATRA evaluation design and baseline comparison.]

Figure 4. SATRA evaluation design and baseline comparison.

18.1 Benchmark construction

The benchmark is designed before implementation claims are evaluated. Each case must have ground truth independently of SATRA for: (1) the intended security obligation, (2) the expected secure behavior, (3) whether a candidate mutation truly violates the obligation, (4) whether the pre-change test suite detects the violation, and (5) whether the AI change legitimately refactors the test or weakens its security oracle.

18.2 Independent ground-truth procedure

10. Define the security policy/obligation manually for the benchmark case or derive it from explicit application security annotations fixed before SATRA runs.

11. Have a separate human reviewer verify the intended authorization behavior and expected outcome.

12. Validate each candidate security mutant by executing an independent policy oracle or reference check; do not use SATRA’s test suite as the sole validity oracle.

13. Run the trusted baseline suite against the validated mutant and record the baseline kill/survive result before introducing the AI change.

14. Apply the candidate AI change and repeat the same independent validation.

15. Adjudicate legitimate test refactors separately from weakening cases.

18.3 AI-generated change definition

SATRA is agent-independent. An AI-generated candidate diff is simply the input artifact. During evaluation, candidate changes may come from multiple coding agents, recorded agent commits, or controlled agent-like mutations. The source of the diff is varied to test robustness, but the SATRA decision engine does not depend on an agent transcript or model API.

18.4 Required case labels

Each benchmark instance is labeled outside SATRA as one of: SECURE_NO_TEST_WEAKENING, SECURE_WITH_LEGITIMATE_TEST_REFACTOR, APPLICATION_REGRESSION, ORACLE_WEAKENING, PRE_EXISTING_TEST_GAP, or INCONCLUSIVE/INVALID-MUTANT. These labels are hidden during SATRA evaluation.

18.5 Case categories

-   Legitimate secure refactor: tests and code change while security mutant kill rate remains stable.

-   Test deletion: security test removed.

-   Assertion weakening: expected 403 replaced by 200/2xx or broad truthiness.

-   Mock widening: authorization or authentication component mocked to return success.

-   Fixture weakening: request fixture is changed from unauthenticated to authenticated.

-   Security code regression: AI change weakens access control while tests remain unchanged.

-   Ambiguous mutation: a generated mutant cannot execute reliably and must be excluded from scoring.

18.3 Baselines

  --------------------------------------------------------------------------------------------------------------------------------------------------------------
  Baseline                              Purpose
  ------------------------------------- ------------------------------------------------------------------------------------------------------------------------
  B1 Diff heuristics                    Detect deletion/skip/assertion weakening without behavioral mutation.

  B2 Independent security-test replay   Run the trusted security suite after the AI change without mutation. Tests the claim: “Why not just re-run the suite?”

  B3 Backcheck-style integrity          Generic independent verification + test-manipulation evidence. [R8]

  B4 Generic mutation score             Standard mutation testing without security-obligation targeting.

  B5 Security mutation only             Security mutants without AI-diff/obligation targeting. [R5]

  SATRA                                 Full change-targeted security-obligation + valid security-counterfactual + independent post-change oracle gate.
  --------------------------------------------------------------------------------------------------------------------------------------------------------------

18.4 Primary KPIs

  ----------------------------------------------------------------------------------------------------------------------------------------------------
  KPI                                 Definition
  ----------------------------------- ----------------------------------------------------------------------------------------------------------------
  Security mutation kill rate         Fraction of valid security mutants killed by the post-change security tests.

  Security-test weakening recall      Fraction of deliberately weakened security tests detected.

  False-block rate                    Legitimate secure test refactors incorrectly rejected.

  Silent regression catch rate        Security behavior regressions whose previously passing suite would miss the fault but SATRA flags.

  Mutation validity rate              Fraction of candidate mutants independently confirmed to compile, execute and violate the declared obligation.

  Mutation feasibility rate           Fraction of generated mutants that compile and execute reliably.

  Decision coverage                   Fraction of cases producing PRESERVED/WEAKENED vs INCONCLUSIVE.

  Analysis overhead                   Additional local time vs normal test execution.

  Evidence completeness               Percent of decisions containing change, obligation, mutant and outcome evidence.
  ----------------------------------------------------------------------------------------------------------------------------------------------------

18.5 Ablation studies

-   Remove security-obligation mapping → generic mutation only.

-   Remove targeted mutation → direct diff heuristics only.

-   Remove test-diff analysis → behavior-only evidence.

-   Remove independent baseline replay → agent-reported test output only.

The hypothesis is that the full SATRA chain provides better security-test regression detection with acceptable false blocks and overhead than each simpler alternative. If not, the contribution is not justified.

19. Six Decisive Kill Tests

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Kill test                             Failure condition                                                                                                                                    Action
  ------------------------------------- ---------------------------------------------------------------------------------------------------------------------------------------------------- ---------------------------------------------------------------
  K1 — Generic mutation equivalence     Generic mutation testing matches SATRA on detection, false-block rate and evidence quality.                                                          Kill the research contribution.

  K2 — Security mutation equivalence    Existing security-mutation methods alone provide equivalent detection without obligation/diff mapping.                                               Kill or redesign the mapping contribution.

  K3 — Generic integrity equivalence    Backcheck/mumei + simple policy heuristics provide equivalent results.                                                                               Kill SATRA as a distinct module.

  K4 — Independent replay equivalence   Simply re-running the trusted security suite after the AI change provides equivalent security-regression detection, false-block rate and evidence.   Kill the targeted-mutation layer.

  K5 — Circularity failure              Obligations cannot be derived independently of the tests being evaluated.                                                                            Kill the current methodology; redesign the obligation source.

  K6 — Feasibility/benchmark failure    Valid mutants or independent ground truth cannot be produced reliably within 5 months.                                                               Narrow immediately or kill.
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

19.1 Why these kill tests are part of the research

SATRA is only justified if it adds measurable value over simpler and current approaches. A failed gate is a scientific result: the corresponding contribution is withdrawn or the module is killed rather than defended through wording.

20. Detailed Security-Obligation Model

  SecurityObligation = {
  id: "AUTH-ADMIN-DELETE",
  subject: "unauthenticated | role=user | owner!=resource.owner",
  action: "DELETE /admin/item/<id>",
  expected_outcome: "HTTP 401/403; no state change",
  code_region: "flask route + authorization guard",
  tests: ["test_delete_requires_admin", ...],
  mutation_operators: ["remove_guard", "invert_role", "allow_owner_bypass"]
  }

20.1 Why this is not just a label

The obligation connects the application security meaning to an executable experiment. SATRA does not rely on a string such as “test_delete_requires_admin” alone. It needs a security operation, an expected denial behavior, a code region and one or more executable security mutants.

20.2 Security mutant example

  Original:
  @requires_role("admin")
  def delete_item(...):
  ...
  Mutant:
  # authorization removed for test-only mutant
  def delete_item(...):
  ...
  Expected security effect:
  unauthorized request may reach privileged operation
  Test expectation:
  test_delete_requires_admin MUST FAIL on this mutant.

20.3 Interpretation

If the test still passes on the mutant after the AI change, the test no longer verifies the intended security property strongly enough. SATRA reports WEAKENED.

21.1 Concrete interaction with CAVR

CAVR can repair dependency choices and then re-verify the resulting project. SATRA does not re-run CAVR’s package behavior analysis. Instead, if a CAVR repair modifies application-level security behavior or its associated tests, SATRA can independently check whether the security-test oracle for that behavior remains intact. The handoff is evidence, not a duplicated analysis.

21.2 Concrete interaction with SABLE

SABLE analyzes IaC security obligations and resource lineage. SATRA does not analyze Terraform resources. If the final ASENT workflow includes application-level code/tests and IaC changes in the same candidate, the two modules publish separate evidence records that the integration layer combines.

24. Ethics, Safety and Experimental Controls

-   All mutants are generated in disposable local repositories or containers.

-   No production credentials or real user data are required.

-   Security regressions are synthetic or drawn from openly available code with safe local execution.

-   No live third-party exploitation is necessary.

-   Results are reported as bounded test-integrity evidence, not as proof of absolute application security.

24.1 False-assurance control

The most dangerous SATRA failure is a false PRESERVED result. The proposal therefore treats mutation feasibility, obligation mapping quality and security-mutant coverage as first-class measurements. A high INCONCLUSIVE rate is preferable to an unjustified security guarantee during the research phase.

27. Final One-Page Summary

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Problem
  An AI coding agent can make a repository “green” by weakening the test oracle: deleting a security test, weakening an assertion, changing a denial test into an acceptance test, or mocking away the authorization decision.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  What SATRA does
  Maps the AI change to a bounded application-security obligation, creates small security mutants that intentionally violate that obligation, and independently runs the post-change security tests to see whether they still detect the fault.
  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Unique boundary
  The contribution is not test linting, mutation testing, security mutation, or AI security scanning alone. It is the change-targeted chain: AI diff → security obligation → targeted security mutant → independent post-change security-test outcome → PRESERVED/WEAKENED/INCONCLUSIVE.
