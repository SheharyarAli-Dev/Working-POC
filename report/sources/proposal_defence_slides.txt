=== SLIDE 2
PROBLEM STATEMENT
2
Dependency layer
A package that is approved by name can still be malicious, compromised or pull an unsafe transitive dependency.
Example: Dormant code reads ~/.aws credentials only when a specific file exists, then calls out to the network.
Application layer
A green test suite does not prove security. A patch or AI repair can keep or introduce an auth/injection flaw; generated tests can be weak.
Example: GET /invoices/<id> returns another user's invoice and every existing test still passes.
Infrastructure layer
A Terraform refactor can stay valid while the least-privilege boundary moves to the wrong logical resource.
Example: After moving S3 into a module, the app role's policy now points at an unrelated bucket.
AI-assisted software development can produce a functionally correct system while introducing security risks across dependencies, application code, and infrastructure, which conventional tests and isolated scanners may not fully detect.
NOTES: “Suppose a developer gives a coding agent an SRS for InvoiceHub. The agent is asked to build an application where users can upload PDF invoices, view only their own invoices, and store them securely using AWS infrastructure.
The agent completes the task, the application runs, and all tests pass. At first, everything looks correct.
But there can still be three different security problems.
First, at the dependency layer, the agent may choose a PDF-processing package that installs successfully, but the exact version or one of its transitive dependencies may be vulnerable or unsafe.
Second, at the application layer, the tests may all be green, but the authorization logic could still be wrong. For example, User A might be able to request User B’s invoice because the generated tests never properly checked ownership.
Third, at the infrastructure layer, the agent may refactor the Terraform for S3 storage. The Terraform may still be valid, but the application’s IAM policy could now point to the wrong bucket.
So the main problem is that the software can appear completely functional while security risks still exist at different layers.
That is why ASENT does not only ask, ‘Does the application work?’ It asks, ‘Is this exact software state safe enough to trust before it is merged?’”

Module | Work | Reported result | Evidence of the gap
CAVR | DONAPI — USENIX Security 2024 | Static + dynamic API-call sequences; handles some obfuscation | Paper reports misses caused by timeouts, sleep, environment variables and external conditions
CAVR | DySec — IEEE TIFS 2026 | eBPF, 36 behavior features, 95.99% accuracy | Install-time observation does not guarantee hidden trigger conditions were reached

CAVR | OSV-Scanner guided remediation | Minimal lockfile fixes for known vulnerabilities | Cannot repair unknown malicious behavior with no CVE record
SATRA-RV | SWE-Mutation — ACL Findings 2026 | Mutation-based evaluation of LLM-generated test suites | Generated suites showed weak power to detect realistic faulty changes
SATRA-RV | ImpossibleBench — ICLR 2026 | Benchmarks coding-agent shortcut behavior | Agents can exploit or manipulate tests — a green suite is not proof
SATRA-RV | Vulnerability-regression research — AITest 2026 | Studied LLM-generated security patches | Fixing the targeted bug and being regression-safe are different properties
SABLE | TerraProbe — 2026 | Layered oracle for LLM-assisted Terraform repair | Scanner-passing "deceptive fixes" exist
SABLE | Trivy / Checkov documentation | Candidate-centric Terraform security checks | Documented limits on plan JSON and some inter-resource references; no baseline-to-candidate attribution
NOTES: Existing security tools already solve important parts of these problems, and ASENT does not replace them.
Package analyzers can detect suspicious behavior, static-analysis tools can find code vulnerabilities, and tools such as Checkov and Trivy can detect many Terraform issues.
But their guarantees stop at different points.
A normal sandbox may miss dormant behavior, a green test may still be a weak security test, and a Terraform scanner may not know whether a security relationship remained attached to the correct logical resource after a refactor.

=== SLIDE 13
INTEGRATED RUNTIME FLOW
13
One candidate workspace → surface router launches only the applicable module(s) → shared evidence & invalidation layer → one final ASENT trust gate (ACCEPT / BLOCK / HOLD).
NOTES: Finally, this is how the complete system works.
There is one untrusted candidate workspace. A surface router checks what the agent changed and activates only the relevant modules.
Their results go into a shared evidence and invalidation layer.
This is important because evidence can become stale. For example, if CAVR repairs a dependency and that affects application code, previous SATRA evidence may need to be rerun. Similarly, if SATRA introduces a new dependency, CAVR must verify it.
Finally, there is one ASENT trust gate.
If all applicable evidence is current and acceptable, the candidate is ACCEPTED. A security failure causes BLOCK, and uncertain evidence causes HOLD for human review.
So the coding agent generates the software, but ASENT independently decides whether that exact candidate has enough evidence to become trusted.

=== SLIDE 27
APPENDIX — ANTICIPATED QUESTIONS
27
What is the input?
SRS / requirements / approved plan + repository and policies. ASENT does not start from a package.
Where does ASENT sit?
Between the untrusted candidate workspace and the point of trust / merge. CAVR also sits synchronously before dependency execution.
How does it obtain context?
Hooks give the event; ASENT reads the SRS / plan, Git, manifests, imports, call sites, tests and Terraform directly.
Do you sandbox thousands of packages every run?
No. Fast evidence is checked broadly; deep counterfactual sandboxing is selective and cached by artifact / context digests.
How do you define suspicious behavior?
Known-risk data plus a sensitive behavior / trigger vocabulary, compared against a project-specific capability contract.
Can a popular package still be malicious?
Yes. Trust is based on the exact artifact, version, path and behavior — not reputation.

=== SLIDE 28
APPENDIX — ANTICIPATED QUESTIONS (2)
28
What about the generated application code?
SATRA-RV owns that boundary and validates every repair independently.
Why SABLE if Checkov exists?
Checkov checks candidate facts; SABLE tests whether the historical obligation stayed on the correct logical successor.
Why not one module?
Dependency behavior, app security and IaC attribution are different objects with different evidence; one classifier would weaken each.
What if a module is uncertain?
The candidate is held for human review. Uncertainty is never silently converted to "safe".
What is automated?
Routing, analysis, CAVR / SATRA repair loops, re-verification, evidence and gating. Humans only for unresolved states.
Why four iterations?
Each iteration ends at an FYP milestone with an integrated, demonstrable increment; modules progress in parallel.

=== SLIDE 32
HOW ONE RUN WORKS
32
ASENT supports both initial generation and later modification — it does not start from a package.
1
Project registration
Developer supplies SRS / approved plan, repository and policies. ASENT creates a run ID and immutable baseline reference.
2
Candidate workspace
The agent works in a Git branch / worktree. Nothing there is trusted or merged automatically.
3
Context & event capture
Hook / tool adapter + shell gateway see tool calls; a Git/file observer records changed artifacts.
4
Surface routing
Dependency action → CAVR · app code/tests → SATRA-RV · Terraform with a protected baseline → SABLE.
5
Module execution
CAVR can block synchronously before a dependency runs; SATRA-RV and SABLE analyse snapshots in parallel.
6
Cross-module invalidation
If a repair changes another module's inputs, only that evidence is invalidated and re-run.
7
Final trust gate
Candidate is frozen; all applicable module states decide: accept & recommit, block & iterate, or hold for review.

=== SLIDE 33
WHERE ASENT GETS ITS INFORMATION
33
The hook is a sensor
It only tells ASENT that a tool is about to run: command, tool type, working directory, run ID. It cannot know why a package is needed.
The context service gives meaning
It reads explicit project artifacts directly — never an LLM summary alone. Every module decision is tied to input hashes, so stale evidence cannot survive a change.

=== SLIDE 34
APPLICABILITY & BLOCKING SEMANTICS
34
Event / surface | Module | Timing | Blocking result
pip/npm install, manifest or lockfile edit, transitive resolution | CAVR | Synchronous, before real execution; cached fast path allowed | REJECTED blocks · UNRESOLVED holds · VERIFIED / RESTRICTED continue
Application source / test generation or modification | SATRA-RV | Incremental in background; mandatory check at freeze | REJECT blocks · RETRY loops · INCONCLUSIVE holds · ACCEPT passes
Terraform / HCL generation or refactor with a protected baseline | SABLE | Parallel static analysis of the candidate snapshot | REGRESSED blocks · UNKNOWN holds · PRESERVED passes
No applicable artifact for a module | N/A | Skipped | Does not block
Why parallel execution is safe
Every output is tied to the same frozen snapshot (or an explicitly versioned one).
Parallel ≠ independent commits — no module can promote the candidate alone.
A repair creates a new snapshot ID and invalidates affected evidence, so an old "green" cannot survive.
Only CAVR is synchronous, and only where a dependency would otherwise touch the environment.

=== SLIDE 39
CROSS-MODULE INTERACTION & INVALIDATION
39
Modules are specialized, not isolated — they share the run and exchange only bounded evidence and invalidation events.
Triggering event | Immediate module | Cross-module consequence
CAVR changes package version / path only | CAVR re-verifies | SATRA reuses evidence if source, tests and imports are unchanged
CAVR replaces a package and updates imports / adapter | CAVR → SATRA | SATRA re-checks changed call sites, security behavior and tests
SATRA repair adds or changes a dependency | SATRA → router → CAVR | CAVR must verify it before the SATRA repair is finally accepted
SATRA repair changes only app logic / tests | SATRA | SABLE stays valid unless Terraform inputs changed
SABLE reports REGRESSED | SABLE | Candidate blocked; corrected Terraform becomes a new SABLE candidate
SABLE fix touches app config or dependencies | Router | Re-run only the affected CAVR / SATRA evidence
SRS or security policy changes | Context service | Invalidate every contract / obligation whose authority changed

any | REJECT | any | BLOCK — SATRA repair / revision

any | INCONCLUSIVE | any | HOLD — human review
any | any | UNKNOWN | HOLD — human review
ACCEPT
Every applicable module passes on the same final snapshot → commit + combined assurance report.
BLOCK / ITERATE
Any blocking failure stops the whole candidate; repair or revision creates a new candidate.
HOLD
Any uncertain result goes to a human. Uncertainty is never silently converted to "safe".
