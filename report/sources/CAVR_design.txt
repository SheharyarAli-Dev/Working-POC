Executive Summary

CAVR is a proposed local security middleware placed between dependency actions in AI-assisted development and the trusted project environment. It assumes that normal requirements gathering and planning have already happened: requirements, skills, allowlists or lockfiles can tell the coding agent which dependency is permitted, but they do not prove that the exact package version, artifact or transitive dependency tree is safe. CAVR therefore verifies the software that is actually about to enter and execute rather than relying on the weaker assumption that an agent will randomly choose the wrong package.

The system captures dependency-changing tool requests before real execution, checks whether the action is permitted by the approved project policy, extracts task and repository context, infers a minimum capability contract, resolves the exact package and transitive graph, discovers security-sensitive trigger conditions, creates synthetic counterfactual environments to activate dormant behavior, observes operating-system effects, builds a causal capability graph, and makes an evidence-based decision. Rejected or unresolved dependency states never reach the trusted project directly; CAVR attempts a minimal safe repair, re-runs both functional and security verification in a fresh sandbox, reconstructs an accepted state from the trusted baseline, and emits bounded assurance evidence.

The research problem is not package hallucination alone and not generic malware classification. Package hallucination/slopsquatting remains one threat path, but CAVR is also intended for correctly specified packages that are compromised, malicious, vulnerable, or pull unsafe transitive dependencies. Existing work already provides strong static, dynamic, graph-based and ML-based package detectors. The harder gaps targeted here are incomplete activation of condition-dependent behavior, project-context-free decisions, cross-package causal behavior, automated compatible repair, and defensible evidence that the accepted state was cleanly reconstructed under a declared security boundary.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Important scope statement: CAVR will not claim that an arbitrary compromised computer is absolutely safe. Its trust claim is bounded: untrusted dependency execution occurs in a disposable transaction; only changes that pass the functional and security obligations are reconstructed into a clean environment; the assurance record states what was verified and what remains unresolved.

2. Problem, Motivation and Real-World Need

2.1 The Core Problem

The core problem begins after an implementation plan or dependency requirement exists. A dependency action can be permitted by the project and still be unsafe because the exact release, artifact, transitive dependency, install script or runtime behavior may be compromised or malicious. Package hallucination/slopsquatting is one real threat path, but CAVR does not depend on the assumption that well-configured coding agents routinely ignore complete requirements.

A correctly chosen dependency can still become a supply-chain risk through compromised maintainers or release infrastructure, dependency confusion, malicious transitive dependencies, unsafe versions, install-time payloads, dormant condition-triggered behavior or native components. Therefore CAVR separates two questions: (1) is this dependency action permitted by the approved project plan/policy, and (2) is the exact code that is about to execute justified and trustworthy enough under the declared security model?

  --------------------------------------------------------------------------------------------------------------------------------------------------
  Requirements vs. CAVR security boundary
  Requirements / Plan Mode answer: “What dependency may be used?”
  CAVR answers: “Is the exact dependency version, artifact, transitive tree and observed behavior that is about to execute safe for this project?”
  If a requested dependency is not permitted, CAVR can block immediately. If it is permitted, security verification still continues.
  --------------------------------------------------------------------------------------------------------------------------------------------------

2.4 Problems CAVR Intends to Solve

-   A dependency action can reach the host before meaningful behavioral verification, even when the package was explicitly approved by the project.

-   Dormant malware stays quiet unless a specific secret, file, hostname, date, platform or environment variable exists.

-   Static analysis can miss dynamically generated/obfuscated/native behavior; ordinary dynamic analysis can miss untriggered paths.

-   Known-malware classifiers can miss new attacks whose exact behavior was never in the training set.

-   Per-package decisions can miss attack paths distributed across transitive dependencies.

-   Detectors often stop at "malicious" and leave the developer to repair the dependency graph manually.

-   Post-repair claims are often vague; a system may say "fixed" without stating what was actually verified.

3.3 Objectives

1. Build a local execution gateway that intercepts pip/npm, manifest and lockfile dependency actions initiated by a coding agent or developer before real execution.

2. Derive a project-specific minimum capability contract from call sites, data inputs and declared task intent without requiring a paid LLM.

3. Discover security-relevant environment predicates and prioritize them by risk and reachability.

4. Automatically synthesize safe fake environments and canary secrets to activate hidden branches.

5. Observe file, process, network, secret and syscall effects and connect them into a cross-package causal graph.

6. Enforce VERIFIED, RESTRICTED, REJECTED or UNRESOLVED outcomes before trusted commit.

7. Automatically search for a safe version/path or supported replacement, and verify it functionally and security-wise.

8. Reconstruct the accepted state from a clean baseline and generate tamper-evident evidence and residual-uncertainty reporting.

4.2 The Specific Gap CAVR Targets

The proposed contribution is not "combine static and dynamic analysis"; that already exists in MalOSS, DONAPI and ProfMal. It is not "scan dependencies"; HERCULE and multiple commercial/open tools already do this. It is not "repair vulnerabilities"; OSV-Scanner already performs dependency-graph remediation for known vulnerability records. The proposed research focuses on three harder links that remain weak when treated separately:

-   Purpose-aware verification: judge security-sensitive behavior against what the current project actually needs from the dependency, rather than only against known-malware similarity.

-   Counterfactual activation: automatically discover and synthesize security-relevant environment conditions so dormant behavior is actively tested rather than passively awaited.

-   Verified repair and bounded assurance: compute a minimal safe dependency repair, reconstruct it from a clean baseline, and state exactly which functional/security obligations were satisfied and what uncertainty remains.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Novelty caution: These are proposed research contributions, not pre-proven novelty claims. The final thesis must report the literature search, implemented algorithms and empirical comparison. CAVR should claim superiority only where experiments support it.

6. Deep Technical Design

6.1 Step A - Interception Gateway, Requirement Gate and Context Extraction

CAVR does not depend on the coding agent voluntarily calling a security API. The execution environment is configured so dependency-changing actions are captured before real execution. The preferred path is an agent-specific pre-tool hook/adapter that receives the structured shell/tool request (command, working directory, repository, task/run identifier and changed files) and forwards it to a local CAVR daemon over a Unix domain socket or localhost API. A second enforcement layer places CAVR-controlled pip/npm wrappers earlier in PATH so direct package-manager calls resolve to the wrapper rather than the real executable. Manifest and lockfile changes are also detected before dependency resolution. The gateway first checks the approved plan/skills/allowlist/lockfile: an unpermitted dependency is blocked immediately. For a permitted action, CAVR then extracts the project context using Git diff, imports, AST/Tree-sitter call sites, manifests and dependency relationships and redirects the request into a disposable analysis transaction. Only an explicit CAVR release decision allows the real dependency state to be reconstructed.

6.2 Step B - Capability Contract Inference

The capability contract is a minimum set of security-sensitive actions justified by the package usage. It is derived from the actual code path rather than from a free-form LLM opinion. The first prototype will use deterministic mappings and program evidence; an optional local model can be studied later, but it is not required.

  -----------------------------------------------------------------------
  Example task: extract text from invoice.pdf
  Used APIs: PdfReader(path), page.extract_text()
  Inferred capability contract:
  ALLOW: read supplied PDF files, memory use, temporary local files
  DENY by default: ~/.ssh, ~/.aws, browser data, arbitrary shell,
  unrestricted network, persistence, credential stores
  -----------------------------------------------------------------------

  -----------------------------------------------------------------------

A practical representation is a capability vector/set such as FILE_READ(scope), FILE_WRITE(scope), NETWORK_CONNECT(scope), PROCESS_EXEC, SECRET_READ(class), PERSISTENCE_WRITE and NATIVE_EXEC. Each inferred capability has evidence and confidence so the policy can distinguish required, optional and unexplained behavior.

6.3 Step C - Security-Relevant Trigger Discovery

Static parsing (Python AST and Tree-sitter) searches for conditions that control security-sensitive code. CAVR does not attempt full symbolic execution. It specifically targets predicates that commonly hide behavior: environment-variable checks, file existence, hostname/user/platform checks, clock/date checks, sleeps/timeouts, container/sandbox checks, CI/cloud metadata checks and external-response conditions.

Each trigger is connected to reachable sensitive sinks. A trigger is high priority when satisfying it can reach a secret read, process execution, persistence write, external connection or unexplained native component.

  ----------------------------------------------------------------------------------------
  Priority(trigger) = sink_risk * reachability_confidence * novelty / estimated_run_cost
  High priority examples:
  getenv("AWS_SECRET_ACCESS_KEY") -> network send
  exists("~/.ssh/id_rsa") -> file read -> network
  date > T -> exec shell
  Low priority example:
  screen_width > 800 -> UI formatting
  ----------------------------------------------------------------------------------------

  ----------------------------------------------------------------------------------------

6.4 Step D - Adaptive Counterfactual Activation

This is the core detection research. Instead of executing one generic sandbox run, CAVR automatically changes only high-risk environmental facts and re-runs the package. It creates fake credentials, fake sensitive files, synthetic hostnames, controlled time values and other non-real canaries. New behavior discovered in one run can reveal another predicate, which is added to the frontier.

  -----------------------------------------------------------------------
  Frontier <- prioritized security triggers
  while budget remains and Frontier not empty:
  t <- highest-priority unexplored trigger
  E' <- synthesize safe environment satisfying t
  trace <- execute package in disposable overlay under E'
  graph <- merge(trace)
  add newly discovered sensitive predicates to Frontier
  stop early on decisive prohibited behavior
  -----------------------------------------------------------------------

  -----------------------------------------------------------------------

The algorithm is intended to be cheaper than exhaustive symbolic execution because it explores security-relevant conditions only. Analysis ends when the risk budget is exhausted, coverage stabilizes, or a decisive violation is observed. Unreached high-risk conditions are reported as residual uncertainty rather than silently assumed safe.

6.5 Step E - Runtime Observation and Cross-Language Normalization

The sandbox monitors operating-system-visible behavior using eBPF/bpftrace where available, with strace/ptrace-style fallback for prototype portability. Events are normalized into semantic actions such as FILE_READ, FILE_WRITE, SECRET_ACCESS, PROCESS_CREATE, NETWORK_CONNECT, EXECUTE_BINARY and PERSISTENCE_WRITE. This captures effects from Python, JavaScript, shell code and native components even when a source parser cannot fully understand the implementation.

Real credentials are never placed in the sandbox. Canary values are used instead. If a canary flows into process arguments, files or outbound traffic, CAVR has direct evidence of attempted secret propagation without exposing actual secrets.

6.6 Step F - Causal Capability Graph

All static and dynamic evidence is merged into a graph G = (V, E). Nodes represent packages, modules/functions, processes, files, secrets, endpoints, environment predicates and dependencies. Edges represent calls, reads, writes, spawns, connects, depends_on, conditioned_by and derived_from. This allows CAVR to reason over a chain rather than a single suspicious API.

  --------------------------------------------------------------------------
  CANARY_AWS
  | read_by
  Package A
  | data_to
  Package B
  | passed_to
  Package C
  | network_send
  external endpoint
  Decision: the end-to-end secret -> external-network path violates the
  capability contract even if no single package performs the whole attack.
  --------------------------------------------------------------------------

  --------------------------------------------------------------------------

6.7 Step G - Policy and Decision

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  State                   Meaning                                                                                                              Automatic action
  ----------------------- -------------------------------------------------------------------------------------------------------------------- --------------------------------------------------------------
  VERIFIED                Observed/evaluated behavior fits the capability contract and required checks pass.                                   Proceed to clean reconstruction/commit.

  RESTRICTED              Package is needed but should operate with narrower filesystem/network/process capabilities.                          Generate enforcement policy and commit under restrictions.

  REJECTED                Strong evidence of unjustified security-sensitive behavior, known malicious status, or prohibited dependency path.   Block and start repair.

  UNRESOLVED              High-risk condition or behavior cannot be sufficiently verified within the analysis budget.                          Fail closed for autonomous mode and start repair/quarantine.
  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

6.8 Step H - Transactional Isolation: Prevent Before Repair

Untrusted installation occurs in a copy-on-write/disposable environment. Local filesystem effects, processes and dependency changes are never committed directly to the trusted project. This changes the recovery problem: instead of trying to perfectly undo malware after it touched the developer environment, CAVR discards the transaction and reconstructs an approved state from a clean baseline.

  -----------------------------------------------------------------------
  Trusted baseline B
  |
  +--> disposable overlay O --> analyze package X
  |
  reject ----------+--> destroy O
  verify ----------+--> reconstruct from B + approved artifacts
  -----------------------------------------------------------------------

  -----------------------------------------------------------------------

6.9 Step I - Automated Minimal Safe Repair

If a package/version is rejected, CAVR builds a repair search over the dependency graph. For version-level repair, variables represent allowable versions and constraints represent SemVer/dependency requirements. The solver excludes rejected versions/paths and minimizes disruption. Z3 can be used for the constraint portion.

  -----------------------------------------------------------------------
  Minimize:
  w1*(direct dependencies changed)
  + w2*(version distance)
  + w3*(files/API call sites changed)
  + w4*(new security risk)
  Subject to:
  rejected package/version/path is unreachable
  dependency constraints are satisfiable
  candidate has no blocking known vulnerability
  candidate passes functional + security re-verification
  -----------------------------------------------------------------------

  -----------------------------------------------------------------------

Repair levels are attempted from least disruptive to most disruptive: (1) safe patch/minor version, (2) safe parent/transitive path, (3) direct-dependency upgrade/override, and (4) supported package replacement. For an entirely malicious/slopsquatted package, CAVR searches alternatives based on the API slice actually used by the project, not on whole-library equivalence. Initial FYP support should limit automatic adapters to clearly mappable APIs/templates; unsupported semantic migrations return UNRESOLVED rather than inventing risky code.

6.10 Step J - Re-Verification

A repair is not accepted because dependency resolution succeeds. The candidate is installed in a fresh disposable environment, project tests/build checks are run, the capability contract is recalculated if the API changed, counterfactual security analysis is re-run, the dependency graph is scanned again, and blocking known vulnerabilities are checked through OSV/public data. A failing candidate is rejected and the next repair is tried.

6.11 Step K - Clean Commit and Bounded Assurance

CAVR never promotes a contaminated sandbox as "clean." It reconstructs the final accepted environment from the trusted baseline plus approved artifacts/manifest changes. Evidence is hash-chained so later modification is detectable. The assurance certificate lists the baseline digest, package/artifact digests, capability obligations, triggered conditions, unresolved conditions, functional checks, dependency-graph status, security checks and residual uncertainty.

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Trust claim: CAVR proves obligations under its declared boundary; it does not claim universal absence of malware. The strongest claim is: no unapproved analyzed transaction was committed; the accepted dependency graph excludes rejected paths; observed/forced behavior satisfied the declared capability policy; the accepted state was reconstructed from the declared baseline; and unresolved coverage is explicit.
  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

7.3 Recommended Demonstration Scenarios

-   Approved benign dependency: agent follows the plan correctly; CAVR verifies the exact version/transitive tree and allows a clean installation with evidence.

-   Known vulnerable dependency: blocked or repaired using public vulnerability data.

-   Trigger-dependent sample: only reveals network/secret behavior after a fake environment variable/file is created.

-   Transitive malicious sample: root dependency looks benign but a nested package creates the prohibited path.

-   Hallucinated/slopsquat-like package: retained as one threat scenario, but not the primary assumption; existence does not bypass behavioral verification.

-   Repair scenario: rejected version is replaced by a safe compatible version/path and re-verified.

-   Unresolved scenario: insufficient coverage causes fail-closed quarantine instead of a false "safe" verdict.

8. Differentiation and Expected Effectiveness

8.1 How CAVR Differs from Existing Solutions

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Existing approach                 Primary decision basis                                                      What CAVR changes
  --------------------------------- --------------------------------------------------------------------------- ----------------------------------------------------------------------------------------------------------------------
  Hallucination prevention [2][3]   Prevent the LLM from producing fake names.                                  Assumes prevention can fail; verifies the dependency before trusted commit.

  NymGuard [4]                      Reserve unclaimed hallucinated names.                                       Works even when a package already exists; asks whether behavior is justified.

  DONAPI [8]                        Known/learned sensitive API-call behavior from static + dynamic analysis.   Adds targeted synthesis of missing trigger conditions and task-specific capability policy.

  HERCULE [9]                       Static integrity/data-flow/transitive analysis.                             Adds dynamic OS behavior and deliberate activation of hidden conditions.

  ProfMal [10]                      Static+dynamic behavior graph classified by a trained graph model.          Uses graph evidence against a contextual capability contract; no mandatory model training.

  DySec [12]                        ML classification of installation-time eBPF traces.                         Uses OS telemetry as causal evidence; explores alternate conditions instead of assuming one trace is representative.

  OSV guided remediation [14]       Known vulnerability record + dependency resolution.                         Repairs unknown behavioral rejection as well as known vulnerable versions; re-runs capability verification.

  RETRO [13]                        Recover after compromise using logged causal history.                       Avoids committing the untrusted transaction; clean state is reconstructed before acceptance.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

8.2 Why the Design May Be More Effective

The expected advantage is structural rather than a guaranteed accuracy claim. CAVR attempts to reduce three sources of false confidence: (1) "not observed" is not treated as "does not exist" because high-risk conditions are actively synthesized; (2) "not known malware" is not treated as benign because behavior is checked against task justification; and (3) "fixed" is not accepted until the repaired state is rebuilt and re-verified. Whether this produces better precision, recall, repair success and assurance usefulness must be demonstrated by the evaluation in Section 10.

8.3 What CAVR Does Not Need to Beat

CAVR does not need to replace every registry-scale malware detector. A registry operator scans millions of packages with different false-positive constraints. CAVR has richer project context and can spend more analysis on the small number of dependencies an agent is about to introduce. This different operating point makes counterfactual analysis and repair feasible without pretending to be a universal package-registry scanner.

9. Training, Data and Dataset Plan

9.1 Is Model Training Required?

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Answer: No mandatory training is required for the core CAVR design. The capability inference, trigger discovery, counterfactual scheduler, causal graph, policy, repair solver and assurance logic are designed to be deterministic/program-analysis based. This keeps the system reproducible, local and free of paid model/API dependencies.
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

A small local ML/embedding model may be explored only as an optional enhancement for package-function similarity or ranking. It must not be a trusted security oracle, and the project remains complete without it.

9.3 Evaluation Datasets

Evaluation can use public research artifacts and controlled inert samples rather than live uncontrolled malware. Suitable sources include the package-hallucination datasets released with Spracklen et al. [2], MalOSS/NDSS benchmark material [5], the HERCULE artifact/benchmark references [9], DySec dataset resources [12], and deliberately constructed benign trigger-conditioned samples that simulate credential/file/network conditions without harming a host. Research malware should remain encrypted and executed only inside isolated laboratory environments according to dataset terms.

9.4 Why No Large Training Dataset Is a Strength

A dataset-dependent classifier can become stale as attacker behavior changes. CAVR still uses known-malware/vulnerability evidence when available, but its central decision asks whether an observed causal behavior is justified by the project. The system can therefore flag a new behavior pattern even if no identical training example exists.

Ablations should disable one CAVR component at a time: no capability contract, no counterfactual activation, no cross-package causal graph, naive repair instead of optimized repair, and no clean reconstruction/assurance evidence.

11. One-Year Research Justification and Milestones

11.1 Why This Is Not a One-Semester "Scanner"

A basic interceptor plus known-vulnerability scanner and one sandbox run can be built early. That would not solve the proposed research problem. The year is justified by separate algorithmic questions that depend on one another: formalizing task-specific capabilities, discovering and prioritizing hidden triggers, synthesizing counterfactual environments, reconstructing cross-package causal behavior, solving minimal dependency repair, and defining/producing bounded assurance evidence. These are new computational capabilities, not time reserved for training, UI integration or repetitive testing.

16. Ethics, Safety, Legal and Threat Model

16.1 Threat Model

Adversary-controlled or compromised third-party dependencies may contain static, obfuscated, dynamically downloaded, native, transitive or condition-gated malicious behavior. The coding agent/developer may unknowingly request such a package. CAVR assumes the Linux host/kernel and CAVR monitor are part of the trusted computing base for the FYP. Kernel/firmware compromise is out of scope.

16.2 Safe Research Rules

-   Use inert canary secrets, never real credentials, in all forced-execution environments.

-   Run malicious research artifacts only in isolated environments with controlled/no external network as required.

-   Do not publish working malicious payloads or live slopsquatting packages.

-   Respect dataset licenses, package-registry terms and responsible-disclosure processes.

-   Label experimental verdicts as research results; do not publicly accuse a package/maintainer without manual validation and responsible disclosure.

-   Assurance reports must state uncertainty and assumptions; never market a bounded result as absolute proof of safety.

16.3 Privacy

The normal system should avoid uploading source code, traces or secrets to external services. Public registry/advisory lookups should send only package identifiers/versions. Local-first processing also supports the project goal of zero paid/API dependency and reduces code leakage.

18.2 Proposed Research Contributions / Novelty Hypotheses

1. Context-derived minimum capability contracts for dependency actions in AI-assisted development, so security decisions are based on what the project actually needs rather than only malware similarity.

2. Security-targeted counterfactual activation: discover high-risk environmental predicates and synthesize safe conditions to deliberately expose dormant behavior under a bounded exploration budget.

3. Cross-package causal capability reasoning that connects task intent, program calls, OS events, canary data flows and transitive dependencies into an explainable policy decision.

4. Verified minimal safe repair: optimize dependency/version/path change for security and compatibility, then re-run both functional and security obligations before acceptance.

5. Bounded assurance by construction: untrusted execution is transactional; the accepted state is reconstructed from a declared baseline and accompanied by tamper-evident evidence plus explicit residual uncertainty.

18.3 Final Research Positioning

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Position: CAVR is best described as an automated pre-commit dependency security middleware for AI-assisted development. It is broader than a slopsquatting detector, more contextual than a generic malware classifier, and more preventive than post-compromise recovery. Its research value depends on demonstrating that counterfactual activation, capability-based causal reasoning, automated repair and bounded assurance materially improve outcomes over simpler baselines.
