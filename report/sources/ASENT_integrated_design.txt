1. Executive Summary

ASENT addresses one practical trust problem in AI-assisted software development: a coding agent can produce a candidate software state that appears functional while risk is introduced at different layers. A dependency can be malicious or compromised, application code can contain or preserve a security defect, and infrastructure-as-code can preserve syntactic validity while the intended least-privilege boundary moves to the wrong logical resource. These are different security objects and require different analysis methods.

The combined project therefore uses three specialized assurance modules under one local ASENT gate. CAVR owns dependency/package behavior before a dependency is allowed to affect the trusted project. SATRA-RV owns application-code security evidence and safe repair acceptance. SABLE owns Terraform/IaC security-boundary continuity. The modules may run in parallel when a feature touches multiple surfaces, but they share a run context, evidence store, candidate workspace and final trust decision.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Whole-project one-liner: The developer gives the SRS/approved plan to the coding agent; the agent works inside an untrusted candidate workspace; ASENT automatically routes dependency actions to CAVR, application security changes to SATRA-RV and Terraform changes to SABLE; only a candidate for which every applicable module passes is committed as the trusted next state.

3. Final Problem, Scope and Security Boundaries

3.1 Combined Problem Statement

AI-assisted development increases the amount of code, dependency resolution and infrastructure configuration that can be produced or modified automatically. The security risk is not limited to hallucinated packages or one class of coding mistakes. A candidate may be unsafe because third-party dependency behavior is malicious, application security logic or tests are weak, or a Terraform refactor silently rebinds a least-privilege authorization boundary. ASENT provides an independent local assurance layer before the candidate is trusted.

3.2 Scope Lock

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Dimension               In scope                                                                                                                                  Not claimed
  ----------------------- ----------------------------------------------------------------------------------------------------------------------------------------- --------------------------------------------------------------------------
  Development mode        Initial AI-assisted generation and subsequent modifications inside a candidate workspace                                                  Universal supervision of every AI tool or every programming language

  Dependency security     Python/PyPI and JavaScript/npm on Linux; direct and transitive dependencies                                                               Firmware/kernel-rootkit/hardware compromise; perfect malware proof

  Application security    Python web applications; bounded families such as auth/authz/IDOR, injection, path traversal, XSS, SSRF, CSRF, insecure deserialization   Universal application-security verification for every framework/language

  IaC security            Terraform/HCL + AWS S3/IAM least-privilege role-to-asset binding during structural refactoring                                            All AWS services, all clouds, or arbitrary Terraform equivalence

  Automation              Automated normal path with bounded retry; uncertain states escalate                                                                       Pretending uncertainty is safe

  Cost                    Local/open-source core, public data, optional local Ollama                                                                                Mandatory paid API/cloud/commercial security service
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

3.3 Why Requirements / Plan Mode Do Not Remove ASENT

The combined design assumes good requirements gathering. The developer can use Plan Mode, skills, allowlists and lockfiles. Those artifacts become inputs to ASENT. They reduce ambiguity, but they do not establish that a permitted package artifact is benign, that generated application code satisfies the intended security semantics, or that a Terraform refactor kept the original authorization boundary on the correct logical asset. Requirements answer what is intended; ASENT verifies what is actually about to be trusted.

4. Integrated End-to-End Architecture

The integration below is the recommended ASENT-wide architecture derived from the three module contracts and the supervisor feedback. It is not presented as a separate novelty claim. Its purpose is to ensure the three research modules operate on one candidate state and cannot produce contradictory “green” outputs that are merged independently.

Figure 1. Whole-project integrated runtime flow: one candidate workspace, event-driven parallel module execution, evidence invalidation, and one final ASENT trust gate.

4.1 Runtime Stages

1.  Project registration: the developer supplies the SRS/approved plan, repository and explicit project/security policies. ASENT creates a run ID and immutable references to the starting repository state.

2.  Candidate workspace: the coding agent works in a Git branch/worktree or isolated candidate workspace. The candidate is not automatically trusted or merged.

3.  Context/event capture: an agent hook/tool adapter and shell gateway observe tool calls, while a Git/file observer records generated/modified artifacts. The context service reads project artifacts directly.

4.  Surface routing: dependency actions trigger CAVR; application code/tests trigger SATRA-RV; Terraform/HCL changes trigger SABLE when its baseline precondition exists. More than one module may run for one feature.

5.  Module execution: CAVR may block synchronously before a dependency executes. SATRA-RV and SABLE may analyze candidate snapshots in parallel. Their outputs are independent evidence envelopes.

6.  Cross-module invalidation: if a repair changes inputs owned by another module, only the affected evidence is invalidated and that module re-runs on the new candidate snapshot.

7.  Final trust gate: ASENT freezes the candidate, checks all applicable module states and either accepts/recommits, blocks/iterates, or holds for human review when evidence is unresolved.

4.2 Applicability and Blocking Semantics

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Event / surface                                                               Module            Execution timing                                                                       Blocking result
  ----------------------------------------------------------------------------- ----------------- -------------------------------------------------------------------------------------- -------------------------------------------------------------------------------
  pip/npm install, manifest/lockfile edit, transitive dependency resolution     CAVR              Synchronous before real dependency execution; cached fast path allowed                 REJECTED blocks; UNRESOLVED holds; VERIFIED/RESTRICTED continues under policy

  Application source/test generation or modification                            SATRA-RV          Incremental/background during development; mandatory freeze-time check before commit   REJECT blocks; RETRY loops; INCONCLUSIVE holds; ACCEPT passes

  Terraform/HCL generation or refactoring with an existing protected baseline   SABLE             Parallel static analysis on candidate snapshot                                         REGRESSED blocks; UNKNOWN holds; PRESERVED passes

  No applicable artifact for a module                                           N/A               Skipped                                                                                Does not block

5. Shared Context, Interception and Routing - How the System Actually Gets Information

5.1 The Hook Is an Execution Sensor, Not the Source of Security Meaning

This directly answers the supervisor’s “how will it get the information?” question. A pre-tool hook or adapter can tell ASENT that the agent is about to execute a command such as `pip install X`, and can provide the command, tool name, current working directory and session/run identifiers. It cannot magically know why X is needed. The context service obtains that meaning from explicit project artifacts.

5.3 Context Integrity Rules

-   ASENT should never depend on an LLM summary as the only source of context; the repository and approved artifacts are the authoritative evidence.

-   Every module decision is tied to input hashes so stale evidence cannot survive after the candidate changes.

-   Project policy changes invalidate contracts derived from the old policy even if source files did not change.

-   Only the minimum change-local context is passed to the SATRA local model; SABLE does not require an LLM in its decision path; CAVR core decisions remain deterministic/program-analysis based.

6. Module 1 - CAVR: Dependency / Package Trust

6.1 Exact Problem

CAVR starts when a dependency action is about to occur. The package may be explicitly required by the approved plan, selected by the coding agent, already present in a manifest, or pulled transitively. The question is not “did the agent hallucinate it?” The question is whether the exact version, artifact, transitive path and observed behavior are justified for the current project before they affect the trusted environment.

6.2 Supervisor-Aligned CAVR Flow

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

6.3 Performance / Cache Design Required by Supervisor Feedback

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Fast checks are applied to every resolved package node; expensive dynamic counterfactual analysis is selective. A cache hit is valid only when: package ecosystem + name + version + artifact SHA-256 + relevant transitive-subtree digest + capability-contract digest + project policy version + CAVR analyzer version are compatible. If any of these change, the verdict is not blindly reused.
  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

-   Previously VERIFIED artifact, identical dependency subtree and same-or-narrower capability contract: reuse evidence after a lightweight consistency check.

-   New artifact hash, newly widened capability, changed transitive dependency, new install script/native binary, known vulnerability, suspicious trigger pattern or old analyzer version: escalate.

-   High-risk transitive nodes can be sandboxed individually or in bounded dependency groups; CAVR does not need to execute thousands of low-risk unchanged packages deeply on every development run.

-   Cache hit rate, percentage of nodes escalated, p50/p95 latency and counterfactual runs per dependency action are mandatory evaluation metrics.

6.4 CAVR Research Contribution Hypotheses

-   Context-derived minimum capability contracts for dependency actions.

-   Security-targeted counterfactual activation under a bounded exploration budget.

-   Cross-package causal capability reasoning using OS-visible events and canary flows.

-   Constraint-based minimal safe dependency repair followed by functional + security re-verification.

-   Bounded assurance by transactional isolation and clean reconstruction rather than claiming absolute malware absence.

7. Module 2 - SATRA-RV: Application-Code Security Verification and Repair Acceptance

7.1 Exact Problem

SATRA-RV addresses security risk in application code produced or modified during AI-assisted development. A green ordinary test suite is not enough: a patch can preserve or introduce an authorization/injection flaw, a repair can create a new regression, and generated or edited tests may be weak, over-mocked or non-discriminative. SATRA-RV therefore treats the patch, tests and repair proposal as untrusted until independent evidence converges.

7.2 SATRA-RV Flow

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Phase                         Mechanism                                                                                                                                Output
  ----------------------------- ---------------------------------------------------------------------------------------------------------------------------------------- ------------------------------------
  S1 Capture                    Snapshot trusted baseline and candidate, record commit hashes/diff/run ID.                                                               Immutable candidate evidence

  S2 Localize                   Map changed lines to routes/functions/security operations and changed tests using AST/Tree-sitter.                                       Security-sensitive regions

  S3 Security Change Contract   Derive subject, action/resource, expected secure outcome and invariants from app semantics/policy rather than the test name alone.       Independent security obligation

  S4 Deterministic tests        Execute bounded security dictionary tests plus local static evidence (Bandit/Semgrep; CodeQL optional baseline).                         Trusted reproducible floor

  S5 Adaptive tests             Conditionally ask local Ollama for repository-specific tests using minimized change-local context.                                       Untrusted test candidates

  S6 Validate generated tests   Require syntax/import success, secure-baseline behavior, counterfactual discrimination, locality, repeatability and safe side effects.   Accepted dynamic tests only

  S7 Correlate findings         Combine contract, dictionary failures, accepted dynamic tests, static findings and diff signals.                                         Normalized finding/evidence bundle

  S8 Repair proposal            Local Ollama may propose a minimal patch from the evidence bundle; patch applied only in isolated branch.                                Untrusted repair candidate

  S9 Differential sandbox       Run security, functional and runtime/build checks; compare before/after behavior.                                                        Repair-verification evidence

  S10 Decision                  Deterministic evidence gate produces ACCEPT / REJECT / RETRY / INCONCLUSIVE.                                                             Commit eligibility
  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

7.3 Initial Security Families

The latest SATRA-RV design keeps Python web applications as the core scope and proposes deterministic treatment for authentication/authorization/IDOR, SQL injection, command injection, path traversal/unsafe file access, XSS, SSRF, CSRF and insecure deserialization. Secrets/credentials, redirects and additional families are extensions only when benchmark evidence justifies them.

7.4 Why SATRA-RV Is Not “Semgrep + Ollama”

-   Ollama is optional infrastructure, not the final authority. The gate remains functional without it.

-   Generated tests must prove discrimination against a valid security counterfactual before they become trusted evidence.

-   Repair is accepted only after a disposable differential sandbox verifies both the target security contract and functional regression behavior.

-   The novelty hypothesis is the change-targeted evidence protocol, not the existence of mutation testing, test generation, vulnerability scanning or LLM repair individually.

8. Module 3 - SABLE: Terraform Security-Boundary Continuity

8.1 Exact Problem

SABLE is intentionally narrower than generic IaC scanning. It studies one relational security obligation: a designated application IAM role must retain only the intended access to a designated protected S3 data asset when Terraform is structurally refactored. The candidate may be valid and may contain security-looking policies, yet the boundary can be widened, rebound or attached to the wrong successor resource.

8.2 SABLE Flow

  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  ------------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------- -------------------------------------------------------------------

  I2 Normalize                    Parse HCL; normalize resources, modules, addresses, policy documents and references.                                                                  python-hcl2 / HCL parser + Terraform CLI

  I3 Model obligation             Represent principal, actions, protected S3 asset, resource scope and authority source.                                                                Trusted baseline policy + explicit benchmark/security requirement

  I4 Successor hypotheses         Generate candidate successor(s) using type, attributes, references, module position, dependency context, policy-target relation and moved evidence.   Structural + semantic evidence

  I5 Obligation projection        Project baseline role/action/resource boundary onto each plausible successor.                                                                         Correspondence model

  I6 Authorization verification   Evaluate IAM/S3 relation locally; use Terraform plan/Checkov/Trivy evidence where useful.                                                             Local deterministic policy evidence

  I7 Attribution                  Separate true misbinding/regression from legitimate re-expression or ambiguity.                                                                       PRESERVED / REGRESSED / UNKNOWN + trace
  ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

8.3 SABLE Activation in the Integrated Project

The supervisor correctly challenged the idea of tying the entire project to “change.” ASENT itself is not change-only. SABLE, however, has an explicit research precondition: there must be a previously verified Terraform security boundary whose continuity can be evaluated. During first-time Terraform generation, ordinary policy scanning may still run, but the SABLE research contribution is N/A until a baseline protected asset/boundary exists and a later structural refactor creates an attribution problem.

9. Cross-Module Interaction, Parallelism and Evidence Invalidation

9.1 Modules Are Specialized, Not Isolated

The modules do not call each other to repeat analysis. They share the candidate run and exchange only bounded evidence and invalidation events through ASENT. This preserves separation of concerns while ensuring that a repair in one domain cannot leave stale evidence in another domain.

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Triggering event                                        Immediate module                                          Possible cross-module consequence
  ------------------------------------------------------- --------------------------------------------------------- ------------------------------------------------------------------------------------------------------------------------------
  CAVR changes package version/path only                  CAVR re-verifies dependency                               SATRA can reuse evidence if application source/tests/import behavior are unchanged; otherwise re-run affected SATRA regions.

  CAVR replaces package and updates imports/API adapter   CAVR then SATRA                                           SATRA must re-check changed application call sites/security behavior and tests.

  SATRA repair adds or changes dependency                 SATRA proposes patch; router emits new dependency event   CAVR must verify the newly introduced/changed dependency before SATRA repair can be finally accepted.

  SATRA repair changes only application logic/tests       SATRA                                                     SABLE remains valid unless Terraform or IaC inputs changed.

  SABLE reports REGRESSED                                 SABLE                                                     ASENT blocks candidate and gives evidence to agent/developer; corrected Terraform becomes a new SABLE candidate.

  SABLE fix touches application config or dependencies    Router determines affected surfaces                       Re-run only the affected CAVR/SATRA evidence.

  SRS/security policy changes                             Context service                                           Invalidate every contract/obligation whose authority source changed.

9.3 Why Parallel Execution Is Safe

-   All module outputs are tied to the same frozen candidate snapshot or to explicitly versioned intermediate snapshots.

-   Parallelism does not mean independent commits; no module can promote the candidate alone.

-   A candidate repair produces a new snapshot ID and invalidates affected evidence. This prevents a “green” result from an earlier version from surviving silently.

-   CAVR is synchronous only where dependency execution would otherwise cross into the environment; SATRA and SABLE can exploit parallel/background execution to reduce developer wait time.

10. Integrated POC Use Case - One Feature Demonstrating All Three Modules

10.1 SRS

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Build a Flask invoice-processing service. Users can upload PDF invoices, extract text locally, and store/retrieve invoice files from an AWS S3 bucket. A user may access only invoices they own. The application role must have only GetObject/PutObject access to the customer-data bucket. Infrastructure is defined in Terraform.
  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

10.2 End-to-End Demonstration

Development starts: The SRS and repo are registered with ASENT. The coding agent begins in the candidate workspace; nothing is trusted yet.

Dependency action: The agent requests a PDF library. CAVR captures `pip install package-X` before it reaches the real environment.

Fast package gate: CAVR resolves the exact artifact/transitive graph. If no valid cache entry exists and risk signals justify escalation, the package enters deep analysis.

Hidden behavior activation: Normal sandbox execution appears benign. Static trigger discovery finds a branch controlled by an AWS credential/file condition. CAVR injects a fake canary and re-runs; OS tracing shows the canary read and an external connection. The behavior violates the PDF-only capability contract.

Dependency repair: CAVR rejects X, finds a safe compatible version or approved replacement Y, runs project tests and repeats security analysis in a fresh environment. The repaired dependency state becomes VERIFIED.

Application security: The agent creates `GET /invoices/<id>`. SATRA localizes the route and derives the obligation “non-owner must be denied.” The deterministic test dictionary or a validated adaptive test discovers that another user can access the invoice.

Application repair: SATRA correlates the finding, proposes/accepts a bounded repair candidate, and runs before/after security + functional checks in the sandbox. Only an ACCEPT result is emitted.

Terraform refactor: The agent moves S3 resources into a module and rewrites the IAM policy. SABLE maps the original customer-data asset to candidate successors. A policy that appears locally valid is found attached to the wrong successor or widened to an unrelated bucket.

Infrastructure correction: ASENT blocks the candidate; the agent/developer corrects the Terraform. SABLE re-runs and emits PRESERVED when the original least-privilege obligation is correctly projected onto the intended successor.

Final commit: The evidence bus holds CAVR VERIFIED, SATRA ACCEPT and SABLE PRESERVED for the same final snapshot. ASENT creates the clean recommit/handoff and a combined assurance report.

10.3 What the POC Must Visibly Show

-   Live candidate workspace and registered SRS/plan.

-   Tool interception event before package installation.

-   CAVR cache/risk gate showing why a package was or was not deeply sandboxed.

-   At least one controlled dormant trigger that is inactive in the first run and activated by a synthetic condition in the second run.

-   OS-level evidence (file/secret/process/network events) and a capability-policy mismatch.

-   SATRA security contract, deterministic/validated test evidence, repair and sandbox differential result.

-   SABLE baseline asset, successor candidates, authorization relationship and preserved/regressed/unknown evidence path.

-   Combined final gate showing that one blocking module prevents the whole candidate from being committed.

-   After correction, a single final snapshot with all applicable modules passing and a combined report.

12.3 Training / Dataset Position

No mandatory model training or fine-tuning is required. CAVR and SABLE core decisions are deterministic/program-analysis based. SATRA-RV can use a pre-trained local Ollama model conditionally for candidate tests and repair proposals, but generated outputs are independently validated. Public research corpora, controlled inert malicious samples, real/synthetic application security cases and controlled Terraform transformations are used for evaluation rather than for training a single security classifier.

13.2 ASENT-Level Metrics

-   End-to-end false-safe acceptance rate: candidate states containing any ground-truth module failure that ASENT incorrectly accepts.

-   Unnecessary block/review rate on legitimate candidate states.

-   Mean/p95 developer wait time from commit request to final gate result.

-   Percentage of package nodes handled by cache/fast gate versus deep sandbox.

-   Cross-module invalidation rate and re-run cost after automated repairs.

-   Combined evidence completeness: every accepted state must have run ID, candidate hash, module statuses and traceable evidence references.

-   Integrated POC success: one candidate touching dependencies, application code and Terraform must be blocked at each injected fault and accepted only after all three are corrected.

13.3 Kill Tests

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Area                        Failure condition                                                                                      Research response
  --------------------------- ------------------------------------------------------------------------------------------------------ ------------------------------------------------------------------------------------
  CAVR counterfactual layer   One normal sandbox/static baseline detects the same hidden cases with comparable overhead.             Narrow or remove the counterfactual claim.

  CAVR capability model       Task capability contract does not improve false-positive/unknown-behavior decisions.                   Redesign capability inference or treat it as supporting evidence only.

  Integrated layer            Evidence fusion does not prevent any additional unsafe merge relative to correct independent gating.   Do not claim integration novelty; retain it only as implementation architecture.

14. Complex Computing Problem and Seoul Accord Alignment

The combined project meets the complex-computing requirement through its research objects and algorithms, not because three tools are integrated. The hardest work is deciding what behavior is justified, what security obligation should remain true, what resource is the logical successor, which counterfactuals are meaningful, how a repair can be minimal and safe, and when evidence is insufficient to accept a candidate.

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Seoul Accord characteristic                  ASENT-wide evidence
  -------------------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  1. Conflicting requirements                  Security coverage vs development latency; autonomy vs independent verification; detection sensitivity vs false blocks; minimal repair vs compatibility; automation vs fail-safe uncertainty.

  2. Depth of analysis / no obvious solution   No single scanner or test answers whether a package’s hidden behavior is justified, a generated repair is safe, or an IaC boundary stayed on the correct logical asset.

  3. Depth of knowledge                        Program analysis, software supply-chain security, Linux isolation/eBPF, graph algorithms, web security, testing/mutation, automated repair, Terraform/HCL, IAM/S3 semantics and constraint solving.

  4. Unfamiliar issues                         Agentic dependency actions, dormant supply-chain behavior, generated-test weakness, repair-induced regressions and structural IaC security misbinding are current research problems.

  5. Beyond standard practice                  Standards/tools solve pieces, but the module research questions remain empirical and must be compared with strong baselines.

  6. Stakeholder conflicts                     Developers want speed; security reviewers want evidence; CI wants deterministic exit states; maintainers need low false accusation; platform teams need legitimate refactoring.

  7. Significant consequences                  Credential theft, compromised builds, unauthorized data access, merged vulnerable code and unnecessary blocking of legitimate development.

  8. Interdependence                           A CAVR repair can change SATRA inputs; a SATRA repair can introduce a dependency; a Terraform correction changes SABLE evidence. One stale decision can invalidate the final trust claim.

  9. Requirement/cause identification          Legitimate package capabilities, application security obligations and logical Terraform successors are not always explicitly declared and must be modeled from evidence while preserving uncertainty.
  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

17. Risks, Ethics, Safety and Controlled Limitations

  --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Risk / limitation                             Handling
  --------------------------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------
  CAVR path explosion / latency                 Security-relevant trigger frontier, strict budgets, cache/hash reuse, bounded parallelism, residual uncertainty.

  Legitimate package needs sensitive behavior   Project capability contract + scoped permissions + RESTRICTED state; do not classify every network/file action as malware.

  Native/packed package code                    OS-level telemetry can observe effects but is not full binary semantic proof; Linux scope is explicit.

  SATRA generated test is wrong/flaky           Never trusted without secure-baseline + counterfactual discrimination + stability/locality checks.

  SATRA circular security oracle                Contract derives from independent application semantics/policy, not solely from the generated test.

  SABLE ambiguous successor                     UNKNOWN rather than forced PRESERVED; benchmark measures UNKNOWN precision to prevent escape-hatch behavior.

  Malware research safety                       Use inert canaries and controlled research artifacts only inside isolated environments; no live slopsquatting or uncontrolled public malware deployment.

  Privacy / source leakage                      Local-first analysis; no production secrets; public lookups send package identifiers/versions only where possible.

  False accusation of open-source package       Experimental verdicts require manual validation/responsible disclosure before public claims.

  Absolute trust                                No module claims universal safety. Evidence is bounded to the declared monitoring, contract and benchmark assumptions.

Appendix B - Supervisor Question Sheet

  ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Question                                                       Answer
  -------------------------------------------------------------- -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  What is the input?                                             SRS/requirements/approved plan + repository/policies. The project does not start from a package.

  Where does ASENT sit?                                          Between the untrusted AI-assisted candidate workspace and the point of trust/merge; CAVR also sits synchronously before dependency execution.

  How does it obtain context?                                    Hooks give the event; ASENT reads explicit SRS/plan, Git, manifests, imports/call sites, tests and Terraform directly.

  Are we scanning/sandboxing thousands of packages every time?   No. Fast evidence is checked broadly; deep counterfactual sandboxing is selective and cached by artifact/context digests.

  How do you know suspicious behavior?                           Known risk data is one signal; CAVR also has a sensitive behavior/trigger vocabulary and compares observed behavior to project-specific capability justification.

  Can a known popular package still be malicious?                Yes; package trust is based on the exact artifact/version/path and behavior, not reputation alone.

  What about the generated application code itself?              SATRA-RV owns that security boundary and validates repairs independently.

  Why SABLE if Checkov exists?                                   Checkov checks candidate facts; SABLE tests whether the historical least-privilege obligation stayed on the correct logical successor after structural refactoring.

  Why not one module?                                            The objects and evidence are different: third-party dependency behavior, application security/repair, and IaC security-boundary attribution. One generic classifier would weaken each research question.

  What happens if one module is uncertain?                       The candidate is held for review; uncertainty is never silently converted to “safe.”

  What is automated?                                             Normal routing, analysis, CAVR/SATRA repair loops, re-verification, evidence generation and final gating. Humans are required only for declared unresolved/inconclusive/unknown states.

  Why one year?                                                  The hard work is the research algorithms and empirical kill tests, not UI or integration. Modules progress in parallel and the integrated gate is only accepted after their individual claims survive evaluation.
