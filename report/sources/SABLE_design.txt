1. Final Problem Statement
 One problem: Structural Terraform refactoring can change the relationship between an application role, a protected S3 data
 asset, and the IAM/S3 policy realization that restricts access to that asset. The candidate configuration may remain valid and
 may satisfy local policy checks, while it is no longer obvious that the previously verified least-privilege security boundary is still
 attached to the intended logical asset.


The problem is therefore not “does the new Terraform pass a security scan?” A scanner can answer that. The SABLE
research problem is: after Terraform infrastructure is structurally refactored, a previously verified least-privilege
authorization boundary may no longer be attached to the intended logical data asset. The key question is which
candidate resource is the successor of the protected baseline asset and whether the same least-privilege boundary
still governs that successor.

1.2 Why one obligation is enough
SABLE does not need three independent security controls. Encryption, logging, and public-access checks would turn
the module into a compliance checklist. The chosen target is one richer relational obligation: a least-privilege
authorization boundary must continue to protect the intended S3 data asset across structural Terraform change.
Different Terraform constructs are evidence of that same boundary, not separate SABLE projects.

2. Why this is a real security problem
Security-sensitive infrastructure is not just a bag of independent attributes. AWS explicitly describes S3 least privilege
in terms of who receives what permissions and on which S3 resources, and recommends granting only the actions
required for a task. AWS also recommends examining bucket policies and related access-control mechanisms when
determining whether data is publicly accessible or appropriately protected. [R1]

That makes the SABLE target inherently relational: the security meaning depends on the relationship between
principal, action, and resource. A structural Terraform change can alter those relationships even when the individual
blocks still look reasonable.

2.1 The modern trigger: AI-assisted Terraform evolution
The immediate trigger is not “AI is bad.” AI-assisted repair and refactoring are simply an increasingly common source
of rapid infrastructure changes. The relevant research record already documents that security can degrade during
iterative LLM-driven Terraform repair. Our project research record reports 5,968 repair timelines and 4,440 iteration
transitions in the 2026 ESEM study, with 3.3% of scenarios / 5.2% of transitions containing a genuine previously-
passing security regression under the study’s stricter definition; the same record reports resource restructuring as
the dominant classified root-cause category. [R2]
    Evidence-status note: The R2 statistics were already captured in the ASENT research source record used for this design. Live
    web retrieval of arXiv:2608.13404 was intermittently unavailable during final document assembly, so this document does not
    pretend that those figures were freshly re-verified in this exact run.



2.2 Why simple before/after scanning is insufficient as a research question
Before/after security checking answers whether the candidate satisfies a policy as represented. It does not by itself
encode the proposition “this is the same logical protected asset whose least-privilege obligation we previously
verified.” That missing proposition matters most in split, merge, replacement, and multi-resource cases.
SABLE therefore studies attribution, not generic scanning. A final scan remains useful — and becomes one of our
strongest baselines — but it is not the complete research object.

3.1 Impact and hardest limitations of existing solutions
The important question is not whether the existing tools are “good” or “bad.” They each solve real pieces. The
research opportunity exists only if the remaining seam changes a security decision. The most important limitations
relevant to SABLE are therefore:

      Address continuity is not the same thing as security-obligation continuity. Terraform can preserve resource
       identity across supported moves, but an IAM/S3 security relationship can still be rewritten, widened, rebound, or
       become ambiguous.
      Policy checking is usually candidate-centric. It can establish that a given candidate policy is compliant, but our
       target is baseline-to-candidate attribution of the intended protected asset.
      Repair verification is broader than SABLE. TerraProbe and TerraRepair show that safe Terraform repair needs
       multiple layers; SABLE must therefore contribute a narrower attribution problem rather than duplicate repair
       validation.
      Cloud-state monitoring solves a different deployment-time problem. SABLE is intentionally pre-deployment and
       local, so it can be reproduced without AWS credentials.
      Generic “semantic preservation” is already a crowded claim. SABLE must remain Terraform-specific, obligation-
       specific, benchmarked, and bounded.

3.2 What current state of the art tells us
Terraform’s official refactoring documentation explicitly supports moving/renaming resources, moving modules,
creating multiple instances, and splitting modules through moved blocks. [R3] Checkov already contains graph-
based S3 access-control logic rather than only isolated attribute checks. [R4] TerraProbe shows that scanner-passing
Terraform repairs can still be deceptive and reports strong disagreement between targeted finding removal and full
multi-layer validation. [R6] TerraRepair shows that provider/reference grounding and escalation improve repair, but
missing deployment-specific context remains an important boundary. [R7] SCAFFOLD-CEGIS demonstrates that
security constraints can be carried through iterative refinement, so SABLE cannot claim the abstract idea of
preserving security through change. [R8]


4. Exact residual gap
    Residual gap: After strong existing evidence is taken into account, we still need to test whether a bounded Terraform method
    can attribute one previously verified least-privilege S3 security obligation to the correct candidate successor asset after
    structural refactoring — and distinguish preserved, regressed, and unresolvable cases — more accurately than the strongest
    simpler evidence combination.


This is deliberately a hypothesis. We have not proven that existing tools fail on the benchmark. The benchmark exists
to answer that question.

4.1 The exact non-goals
      Not a general Terraform scanner.
      Not a general IAM analyzer for arbitrary AWS services.
      Not an automatic Terraform repair engine.
      Not a replacement for Terraform moved blocks or plan.
      Not a theorem prover for arbitrary semantic equivalence.
      Not a cloud deployment monitor.
      Not an AI agent that supervises another AI agent.
      Not “security is preserved because the new scanner passed.”

4.2 Falsifiability rule
The single most important rule is: if the strongest existing baseline can classify the same hard cases with equivalent
accuracy, false-safe rate, false-regression rate, and evidence quality, the SABLE contribution is withdrawn or
narrowed. The project does not rescue a failed novelty claim through wording.

5.2 Correspondence evidence
For each baseline asset, SABLE generates candidate successor hypotheses. Evidence is gathered from bounded
signals: resource type, normalized attributes, references, module position, dependency context, policy-target
relationship, and explicit Terraform move evidence where available. The method never treats a single weak signal
such as name similarity as proof.

5.3 Obligation projection
The key step is to project the baseline authorization boundary onto each plausible successor. A candidate can fail in
two different ways: the correct successor can have weaker authorization, or a valid authorization boundary can be
attached to the wrong logical successor. SABLE must be able to distinguish those cases.

5.5 Why UNKNOWN is a feature, not an escape hatch
A false PRESERVED result is the dangerous failure mode. UNKNOWN is therefore allowed only when evidence is
quantitatively insufficient under fixed thresholds or when successor hypotheses conflict. The evaluation will measure
UNKNOWN quality separately; a system that sends every difficult case to UNKNOWN has not solved the problem.

5.6 Pseudocode-level decision logic
    baseline = extract_obligation(baseline_tf)
    candidates = generate_successor_hypotheses(baseline, candidate_tf)
    scored = score_correspondence(baseline, candidates, evidence)
    valid = filter_by_confidence_and_constraints(scored)
    projected = project_obligation(baseline.obligation, valid)
    security = evaluate_authorization(projected, candidate_tf)

    if no_unique_successor(valid) or evidence_conflicts(valid):
        decision = UNKNOWN
    elif obligation_holds(security, intended_successor(valid)):
        decision = PRESERVED
    else:
        decision = REGRESSED

    emit_evidence(baseline, valid, projected, security, decision)

9.2 Concrete CAVR/SABLE interaction
A single feature request can touch dependencies and infrastructure. CAVR can produce a dependency-trust evidence
record after its own analysis/repair. SABLE can independently produce an infrastructure security-boundary record for
the Terraform portion of the same change. The handoff is evidence, not duplicated analysis.

9.3 Concrete SABLE/SATRA interaction
If one AI-generated candidate changes both infrastructure and application authorization tests, SABLE analyzes the
infrastructure relation and SATRA analyzes the test oracle. Neither needs to perform the other module’s computation.
The common ASENT layer combines their evidence for the change-level decision.

10.1 One-minute explanation
“Terraform infrastructure is often refactored while features are being developed. Existing security tools can check the
new configuration, and Terraform can track some resource moves. Our problem is harder: when the structure
changes, did the least-privilege boundary that protected the original S3 data asset remain attached to the correct
logical asset? SABLE builds a baseline security-obligation model, maps it to candidate successors using structural
and semantic evidence, re-checks the authorization boundary, and conservatively reports preserved, regressed, or
unknown. We test it against the strongest simpler baselines; if they do the same job, we kill our claim.”
