\chapter{Research and Existing Solutions}

\section{Research Method / Approach}
ASENT studies three related assurance problems: package and dependency risk in generated code (CAVR), security-property regression during code change and repair (SATRA-RV), and continuity of authorization obligations across infrastructure refactoring (SABLE). The integrated research-design document frames these as complementary modules; they have different inputs, threat models, and evidence, so a result in one module is not evidence for another. The mid-stage report describes implemented scope and controlled evidence. It does not present a completed comparative evaluation or claim a demonstrated advantage over existing tools.

\section{CAVR: Package Risk and Generated Dependencies}
Package-name hallucination and malicious-package detection are distinct problems. Spracklen et al. measured package hallucinations across 576,000 generated samples from 16 popular code-generating models; their concern is recommendations for packages that do not exist, not proof that an existing package is malicious \cite{spracklen2025hallucinations}. This supports checking package identity and provenance before relying on generated dependency suggestions, while leaving package behavior and compromise as separate questions.

MalOSS presents a framework for measuring supply-chain attacks in interpreted-language package managers and combines package metadata with static and dynamic analysis; its study identified 339 malicious packages, of which registries confirmed 278 \cite{duan2021maloss}. Vu et al.'s PyPI study, \emph{Bad Snakes}, examined malware-scanning tools and reported substantial false-positive rates among the evaluated tools, underscoring that scanner alerts require careful interpretation \cite{vu2023badsnakes}. These studies concern observed malicious packages and scanner performance in defined datasets. Their findings do not establish an error rate for CAVR or imply that any one scanner is sufficient for a specific dependency decision.

The research question for CAVR is whether a bounded, reproducible gate can combine pinned dependency identity, artifact integrity, metadata consistency, and isolated behavior evidence into explicit outcomes, including unresolved status when evidence is insufficient. The relevant comparison is with established package scanners and supply-chain analysis under a declared dataset and protocol. The mid-evaluation evidence documents the module's implementation and tests; it does not establish comparative effectiveness or a general malware-detection rate.

\section{SATRA-RV: Security Properties During Code Change}
Test-suite behavior is a relevant concern when evaluating automated code changes. ImpossibleBench studies whether coding agents exploit conflicts between natural-language requirements and tests, using tasks where the specification and test oracle are intentionally inconsistent \cite{zhong2026impossiblebench}. This demonstrates a benchmark design for oracle weakness; it is not a measurement of security regressions in ASENT or of all coding agents.

Hora and Robbes analyzed more than 1.2 million commits from 2,168 repositories and compared testing changes associated with coding agents and other contributors. They report higher rates of test-file changes and mock additions in the agent-associated commits they studied \cite{hora2026overmocked}. The presence of mocks alone does not make a test invalid, and the study does not establish that an individual test suite is insecure. OWASP's practitioner guidance separately recommends independent security tests and cautions that generated tests may be weakened or removed to make a build pass \cite{owaspAICoding}.

Related test-quality work provides useful context for this validation problem. SWE-Mutation, a Findings of ACL 2026 benchmark, evaluates generated test suites against 2,636 mutated variants derived from 800 software-engineering instances across nine programming languages; it studies general test discriminative power, not security-specific contracts \cite{sun2026swemutation}. The AITest 2026 study ``Beyond Bypass'' treats regression risk as distinct from fixing the targeted vulnerability and applies differential static analysis to 479 complete C/C++ functions across eight CWE types (1,916 patch--function pairs). Its results are bounded to that dataset and analysis setup, but directly illustrate why target-fix success alone is insufficient evidence about a patch \cite{shahzad2026beyondbypass}.

Liang et al.'s SecTDD study evaluates visible and hidden security tests across 2,705 trajectories, 31 tasks, three secure-code benchmarks, and 16 CWE categories. In this arXiv preprint, visible-test success does not guarantee success on hidden behavior families, and the measured benefit of showing tests varies across model--benchmark conditions \cite{liang2026sectdd}. Surikov's arXiv practicum describes a Python scan--repair--rescan pipeline using CodeQL and Bandit on 26 prompts in nine CWE categories; it reports new findings introduced during remediation in 15--22\% of cases. This is an unpublished practicum report and a different workflow, so it is adjacent evidence rather than peer-reviewed validation of SATRA-RV \cite{surikov2026jit}.

Together, these sources motivate evaluating security properties against trusted tests and explicit counterfactuals rather than treating a green candidate suite as sufficient. None directly validates SATRA-RV's method. Its project question is whether bounded localization, trusted-test comparison, and counterfactual checks provide useful evidence about selected security contracts. The retained report evidence includes an \texttt{INCONCLUSIVE} integrated result and documented test/environment limits; it does not establish general detection accuracy or superiority to other repair-validation methods.

\section{SABLE: Terraform and Authorization Continuity}
Empirical work has studied security-practice adoption in infrastructure as code and how developers interpret static-analysis findings. Verdet et al. analyze Terraform security practices across 812 public projects covering AWS, Azure, and Google Cloud \cite{verdet2025terraform}. Hu et al. characterize 491 alerts from ten open-source Terraform repositories and one proprietary repository, including practitioner perspectives on alert actionability and resource dependencies \cite{hu2023alerts}. These studies describe practice adoption and alert interpretation; neither evaluates whether a particular verified IAM/S3 obligation remains attached to the intended logical asset after a structural refactor. Their samples also bound generalization to other repositories and deployed systems.

Terraform's \texttt{moved} block records a prior and new resource or module address and updates the address in state before planning, avoiding destruction solely because of that address change \cite{hashicorpMoved}. Address migration provides useful refactor evidence, but does not establish that an IAM policy still targets the intended protected asset. AWS documentation distinguishes S3 bucket and object resources and their policy ARN forms \cite{awsS3Policy}; a valid policy and a valid Terraform address therefore answer different parts of the continuity question.

Existing IaC scanners provide relevant baselines but have bounded visibility. Trivy documents support for Terraform configuration and plan inputs while noting limits where values depend on provider state or unresolved expressions \cite{trivyTerraform}. Checkov's graph check for S3 public ACL read is an example of a concrete configuration rule \cite{checkovS3Graph}. These sources support comparison with static checks; they do not show that scanners cannot address identity continuity, nor do they establish the performance of SABLE.

Recent infrastructure-repair studies make the comparison timely. Agyekum and Santos' ESEM 2026 study analyzes 5,968 IaC repair timelines and reports that strict detection found regressions in 3.3\% of scenarios and 5.2\% of transitions; resource restructuring was the dominant root cause in their analysis \cite{agyekum2026fixing}. TerraProbe evaluates 288 Terraform repairs across 68 real-world and 28 injected-defect modules, and reports cases where removing a targeted scanner finding did not establish a correct repair \cite{alsaid2026terraprobe}. TerraProbe is an arXiv preprint submitted to a journal, and both studies use bounded datasets and checks. Neither directly validates SABLE.

\section{Research Gap and Proposed Evaluation}
Across the three modules, the project examines whether assurance evidence remains meaningful under a particular change: dependency selection and execution (CAVR), code repair (SATRA-RV), or infrastructure refactoring (SABLE). This is a project framing, not a claim that prior work has ignored these areas. The module questions and planned comparisons are recorded in the internal integrated research design \cite{asentIntegratedResearchDesign}.

For SABLE specifically, the bounded question is whether an analyzer can verify a registered IAM/S3 obligation on a baseline snapshot, identify a supported candidate successor after a Terraform structural change, and evaluate whether the same obligation holds for that successor, returning uncertainty when correspondence or semantics are ambiguous. The proposed evaluation compares the implemented B0--B4 configurations on controlled scenarios, including candidate-only checks, baseline verification, explicit move evidence, structural correspondence, and obligation projection. Such fixtures can test the stated behavior but cannot substitute for an independently sampled benchmark or live-cloud evaluation. The current report records implementation and focused correctness evidence only: no completed comparative benchmark, independent effectiveness result, external error rate, or live deployment is claimed.

\section{Proposed Solution}
The three modules provide distinct, bounded evidence: CAVR evaluates pinned package artifacts and isolated behavior; SATRA-RV evaluates selected security contracts across code changes; SABLE evaluates authorization continuity across supported Terraform snapshots. The shared workflow binds module evidence to a candidate snapshot and applies integrity and freshness checks before producing an aggregate status. Chapters 5--7 describe implementation; Chapter 8 reports the retained tests and their limits.

\section{Complex Computing Problem and Technical Challenges}
The project combines dependency and artifact verification, bounded execution evidence, code-change localization and counterfactual testing, declarative-language normalization, resource correspondence, and relational authorization evaluation. Each module must preserve uncertainty when its inputs exceed supported semantics. A result in one module cannot resolve another module's uncertainty, and aggregate status depends on evidence being current and bound to the same candidate. The implementations address bounded subsets; complete package-malware coverage, arbitrary program semantics, full Terraform evaluation, complete AWS policy semantics, and live cloud state remain outside the reported scope.

\section{Research Findings and Design Decisions}
The reviewed literature and official technical documentation provide empirical context, baselines, and implementation semantics across all three module areas. They do not establish that ASENT improves on existing tools. Current tests show expected outcomes for selected fixtures and retained runs; they do not demonstrate novelty, general effectiveness, or independent error rates. The research contribution remains a set of bounded questions whose comparative evaluation is future work.
